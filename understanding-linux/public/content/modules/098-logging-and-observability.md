## Core Concepts
### Introduction to Logging and Observability
Logging is the **persistent recording** of discrete events generated by kernel or user‑space components. Each event carries a **facility** (origin subsystem) and a **severity** (importance). Observability extends logging by providing **queryable, correlated telemetry** (logs, metrics, traces) that lets you infer internal system state from external outputs. In Linux, the kernel exposes events via the **printk** subsystem and **netlink** sockets; user daemons forward them to consumers like `rsyslog`, `systemd-journald`, or `prometheus-node-exporter`.

### Syslog Concepts
The syslog protocol (RFC 5424) encodes a message as:

```
PRI HEADER STRUCTURED-DATA MSG
```

* **PRI** = `<facility> × 8 + <severity>` (integer 0‑191).  
  Example: `LOG_DAEMON` (facility = 3) + `LOG_WARNING` (severity = 4) → PRI = 3×8+4 = 28 → `<28>` in the wire format.  
* **HEADER** contains a timestamp and hostname.  
* **STRUCTURED‑DATA** holds key‑value pairs (e.g., `["exampleSDID@32473 iut="3" eventSource="Application" eventID="1011"]`).  
* **MSG** is the free‑form text.

Facilities (`LOG_KERN`, `LOG_USER`, `LOG_MAIL`, `LOG_DAEMON`, `LOG_AUTH`, `LOG_SYSLOG`, `LOG_LPR`, `LOG_NEWS`, `LOG_UUPC`, `LOG_CRON`, `LOG_AUTHPRIV`, `LOG_FTP`, `LOG_NTP`, `LOG_LOGaudit`, `LOG_LOGalert`, `LOG_CLOCK`, `LOG_LOCAL0`‑`LOCAL7`) allow administrators to route messages based on source. Severities (`LOG_EMERG`‑`LOG_DEBUG`) enable filtering by importance.

### Journals and Log Rotation
`systemd-journald` stores entries in a **binary journal** (`/var/log/journal/` or `/run/systemd/journal`). The format is a series of **sector‑aligned blocks** (typically 4096 B) containing:

* A **header** with file magic, sequence numbers, and timestamps.
* An **array of entry objects**, each comprising:
  * A **monotonic usec timestamp** (64‑bit).
  * A **payload** of variable‑length fields (e.g., `_PID=`, `_UID=`, `MESSAGE=`).
  * A **hash table index** for quick lookup by field name/value.

Because entries are appended sequentially, insertion is **O(1)** amortized; retrieval uses the built‑in indexes, giving **O(log N)** lookup for field‑based filters.

Log rotation prevents unbounded growth. Traditional `logrotate` works on plain text files, while `systemd-journald` implements **size‑based** and **time‑based** retention natively:

* **Size retention**: when the journal exceeds `SystemMaxUse=` (default 10 % of `/var` filesystem, capped at 4 GB), the oldest files are deleted until usage falls below `SystemMaxUse=` or `SystemKeepFree=` (default 15 % free space).
* **Time retention**: `MaxRetentionSec=` (default 1 month) deletes files older than the threshold.

### Metrics Basics
Metrics are **numerical time‑series** sampled at regular intervals. In Linux they originate from:

* **/proc** pseudofiles (e.g., `/proc/stat` provides jiffies spent in user, nice, system, idle, iowait, irq, softirq, steal, guest, guest_nice).
* **/sys** (e.g., `/sys/block/sda/stat` for I/O statistics).
* **perf events** and **eBPF** programs that attach to kernel tracepoints or kprobes and increment per‑CPU counters.
* **Prometheus exporters** that scrape `/proc` and expose via HTTP.

A simple CPU utilisation metric can be derived from `/proc/stat`:

$$
\text{CPU\%} = 100 \times \frac{(\Delta user + \Delta nice + \Delta system)}{(\Delta user + \Delta nice + \Delta system + \Delta idle + \Delta iowait + \Delta irq + \Delta softirq + \Delta steal)}
$$

where Δ denotes the difference between two samples taken Δt seconds apart.

## How It Works
### Syslog Message Processing
1. **Generation** – A process calls `syslog(int priority, const char *format, ...)`. The libc wrapper formats the message and writes a **datagram** to the Unix domain socket `/dev/log` (type `SOCK_DGRAM` or `SOCK_STREAM` depending on daemon).  
2. **Reception** – The syslog daemon (`rsyslogd` or `syslog-ng`) binds to `/dev/log`, reads the datagram, and extracts the PRI field.  
3. **Priority decoding** – The daemon computes facility = PRI ÷ 8, severity = PRI % 8.  
4. **Filtering** – The daemon scans `/etc/rsyslog.conf` (or `/etc/syslog-ng/syslog-ng.conf`). Each **selector line** has the form `facility.severity action`. The daemon matches if the message’s facility/severity satisfies the selector (using precedence rules: `*` matches all, `.` separates facility/severity, `=` exact, `!` excludes).  
5. **Action execution** – Depending on the action:
   * **File** – opens/appends to the pathname (with optional `sync` after each write).  
   * **Remote forwarding** – encodes per RFC 5424 and sends via UDP/TCP to `@host:port` (default UDP 514).  
   * **Program** – forks/execs the specified program, piping the message via stdin.  
6. **Persistence** – If the action is a file, the daemon may invoke `fsync()` after each write (controlled by `sync` flag) to guarantee durability; otherwise data may be lost on crash.

*Why this matters*: The PRI encoding lets a single integer convey both taxonomy and urgency, enabling O(1) filtering without parsing the message text.

### Journal Storage and Retrieval
`systemd-journald` receives messages via the same `/dev/log` socket **and** via the kernel’s `journald` log level (`printk` messages are forwarded through a kernel‑to‑userspace relay). Each entry is serialized as:

```
[Header] [Field1='value1'\0] [Field2='value2'\0] ... [MESSAGE='text'\0] [Padding to 8‑byte boundary]
```

Fields are stored as **type‑length‑value (TLV)**. The daemon builds **two in‑memory indexes** per file:
* **Hash table** for `_UID=`, `_PID=`, `SYSLOG_FACILITY=`, etc.
* **B+tree** for monotonic timestamps (enabling range queries).

`journalctl` simply opens the journal(s), applies the requested filters (e.g., `-u sshd.service`, `--since "1 hour ago"`), and streams matching entries to stdout, applying optional output formatting (`-o short`, `-o json`, `-o verbose`).

*Why this matters*: Binary storage eliminates the need for line‑based parsing, reduces I/O (fixed‑size blocks), and allows indexed queries that would be O(N) on flat files.

### Log Rotation and Retention
`logrotate` is invoked by cron (typically daily). Its configuration stanza:

```
/var/log/app.log {
    size 100M          # rotate when file ≥ 100 MiB
    rotate 4           # keep 4 old copies
    compress           # gzip old logs
    delaycompress      # compress from second rotation onward
    missingok          # ignore if file absent
    notifempty         # do not rotate empty file
    create 0640 root adm   # permissions for new file after rotate
    postrotate
        /usr/bin/killall -HUP app-daemon   # signal daemon to reopen logs
    endscript
}
```

When `size` triggers, logrotate:
1. Renames the current file to `app.log.1`.
2. Compresses `app.log.1` (if `compress` set) → `app.log.1.gz`.
3. Shifts older logs (`app.log.2.gz` → `app.log.3.gz`), discarding beyond `rotate`.
4. Creates a fresh `app.log` with `create` mode.
5. Executes `postrotate` scripts (often a `kill -HUP` to make the daemon reopen its log file).

*Why this matters*: Size‑based rotation guarantees a predictable upper bound on disk usage (`size × (rotate+1)`), while time‑based rotation (`daily`, `weekly`) aligns with operational windows (e.g., nightly backups). The `postrotate` step is essential; without it, the daemon continues writing to the moved file, causing **log loss**.

### Metrics Collection and Exposure
A node‑exporter script reads `/proc/stat` every Δt seconds, computes CPU utilisation as shown above, and exposes it via HTTP on `:9100/metrics`:

```
# HELP node_cpu_seconds_total Seconds spent in each CPU mode.
# TYPE node_cpu_seconds_total counter
node_cpu_seconds_total{cpu="0",mode="user"} 12345.67
node_cpu_seconds_total{cpu="0",mode="nice"} 234.5
...
```

The Prometheus server scrapes this endpoint, storing samples in its TSDB. Alerting rules can then be defined, e.g.:

```
ALERT HighCPUUsage
  IF 100 * (rate(node_cpu_seconds_total{mode="user"}[5m] + rate(node_cpu_seconds_total{mode="system"}[5m])) / rate(node_cpu_seconds_total[5m]) > 80
  FOR 2m
  LABELS {severity="critical"}
  ANNOTATIONS {summary="Host {{ $labels.instance }} high CPU usage"}
```

*Why this matters*: Turning raw counters into rates (`rate()`) yields **instantaneous utilisation**, a dimensionless metric suitable for cross‑host comparison and threshold‑based alerting.

## Worked Examples
### Example 1: Configuring Syslog with Priority Math
**Goal**: Forward all kernel messages (`LOG_KERN`) of severity `LOG_ERR` or higher to `/var/log/kern-err.log`; send everything else to a remote syslog collector at `logs.example.com:514`.

1. Compute PRI thresholds:  
   * `LOG_KERN` = facility 0 → base PRI = 0×8 = 0.  
   * `LOG_ERR` = severity 3 → PRI = 0+3 = 3.  
   * “or higher” means numerically **≤ 3** (since lower numbers = higher severity).  
2. Edit `/etc/rsyslog.conf`:

```bash
# Kernel errors and worse to local file
kern.err /var/log/kern-err.log

# Everything else to remote server
*.* @logs.example.com:514
```

3. Restart rsyslog: `sudo systemctl restart rsyslog`.  
4. Verify with logger:  
   ```bash
   logger -p kern.err "Test kernel error"
   grep "Test kernel error" /var/log/kern-err.log   # should appear
   logger -p user.info "Test user info"
   # Should appear in remote collector (check with tcpdump or remote journal)
   ```

*Why this works*: The selector `kern.err` matches any message where facility=`kern` **and** severity ≤ `err`. The wildcard `*.*` catches all remaining facilities/severities.

### Example 2: Journal Query with Time Arithmetic
**Goal**: Count the number of `systemd` service start messages for `sshd` in the last 90 seconds.

1. Determine monotonic time now: `journalctl -o monotonic -n 1 | tail -1` → e.g., `2000000` (usec since boot).  
2. Compute start timestamp: `now_usec - 90*1e6 = 2000000 - 90000000 = -88000000` (negative means boot‑time wrap; journalctl handles relative strings).  
3. Use relative syntax (simpler):  

```bash
journalctl _SYSTEMD_UNIT=sshd.service \
       _TRANSPORT=kernel \
       --since "90 seconds ago" \
       | grep -c "Started OpenSSH Server Daemon"
```

Assume output: `27`.  

*Why this works*: Journal indexes on `_SYSTEMD_UNIT` and timestamps allow the query to be resolved in **O(log N)** time, scanning only the relevant segment.

### Example 3: Log Rotation Size Calculation
**Goal**: Ensure `/var/log/app.log` never exceeds 2 GiB on disk, given an average write rate of 5 MiB/min.

1. Compute time to hit size limit if never rotated:  
   $$ t = \frac{2048\text{ MiB}}{5\text{ MiB/min}} = 409.6\text{ min} \approx 6.8\text{ h} $$  
2. Choose rotation interval smaller than this, e.g., `hourly`.  
3. Set `size 500M` and `rotate 4` → maximum retained size = `500M × (4+1) = 2.5 GiB`. Slightly above target; adjust:  

```bash
/var/log/app.log {
    size 300M
    rotate 5
    compress
    create 0640 app adm
    postrotate
        systemctl try-reload-or-restart app.service >/dev/null 2>&1 || true
    endscript
}
```

Now max size = `300M × 6 = 1.8 GiB` < 2 GiB.  

*Why this works*: The product `size × (rotate+1)` gives the worst‑case disk footprint; picking values below the target guarantees compliance.

## Common Mistakes
| Mistake | What’s Wrong | Why It Matters |
|---|---|---|
| **Using `*.*` without a priority** in `/etc/rsyslog.conf` (e.g., `*.* /var/log/all.log`) | This matches **all** facilities **and** all severities, including debug messages (`LOG_DEBUG`). In high‑traffic systems, debug logs can overwhelm I/O and fill disks rapidly. | Leads to uncontrolled log growth, possible denial‑of‑service on logging subsystem, and obscures higher‑severity signals. |
| **Assuming `journalctl -f` works without persistent storage** | If `/var/log/journal/` is missing or not writable, `journalctl -f` falls back to volatile `/run/systemd/journal`, losing history after reboot. | Operators lose historic context needed for post‑mortem analysis; they may incorrectly conclude a service is healthy because earlier errors vanished. |
| **Neglecting to `kill -HUP` (or equivalent) after log rotation** | The daemon keeps the old file descriptor open and continues writing to the rotated (now moved) file. The new log file remains empty. | Results in **silent log loss**; administrators may believe logging is functional while critical events are discarded. |
| **Setting `compress` but omitting `delaycompress` on the first rotation** | The freshly rotated log is compressed immediately, but some daemons (e.g., rsyslog) may still have an open handle and attempt to write, causing `gzip: stdin: broken pipe` errors and lost logs. | Causes intermittent logging failures that are hard to trace because they occur only during rotation windows. |
| **Using `size` and `daily` together without `maxage`** | `logrotate` will rotate when size threshold is hit *or* when daily period elapses, potentially creating many tiny files if the app bursts. | Increases inode consumption and complicates retention policies; may exceed filesystem inode limits. |
| **Misinterpreting PRI encoding** (e.g., treating PRI as decimal instead of octal) | Configuring a selector like `mail.info` assuming PRI `0x14` (decimal 20) but actually intending `LOG_MAIL` (2) + `LOG_INFO` (6) = 22 (decimal). | Results in messages being routed to the wrong file or discarded, breaking expected monitoring pipelines. |

## Exercises
### Easy
1. **Configure syslog** – Add a rule to `/etc/rsyslog.conf` that logs all `authpriv` messages of severity `warning` or higher to `/var/log/auth-warn.log`. Restart rsyslog and verify with `logger -p authpriv.warning "Test"`.
2. **Journal query** – Use `journalctl` to list the last 5 entries for the `cron` service, displaying timestamps in ISO format (`journalctl -u cron -n 5 -o short-iso`).

### Medium
3. **Log rotation design** – For a web server that writes ~2 MiB/min to `/var/log/nginx/access.log`, craft a `logrotate` stanza that keeps at most 7 days of logs, compresses old logs, and ensures the nginx process reopens its logs after rotation. Explain your choice of `size`, `rotate`, and `maxage`.
4. **Metric derivation** – Write a one‑liner bash script that reads `/proc/stat` twice, one second apart, and prints the instantaneous CPU utilisation percentage (to one decimal place). Use the formula given in the Metrics Basics section.

### Hard
5. **Journal size planning** – Given a system that generates ~150 MiB/journal‑hour and a `SystemMaxUse=` of 4 GB, calculate the maximum retention time achievable before old journals are purged. Show the math and then set the appropriate value in `/etc/systemd/journald.conf`.
6. **eBPF metric** – Attach an eBPF program (using `bpftrace`) to the `sched:sched_switch` tracepoint to count voluntary context switches per second for a specific PID (e.g., `1234`). Output a running average over a 10‑second window. Explain how this metric complements traditional CPU utilisation from `/proc/stat`.

## Linux Connection
The Linux logging and observability stack consists of several tightly integrated components:

* **Kernel event generators** – `printk()` (log level 0‑7) writes to the kernel log buffer; `netlink` (`NETLINK_KOBJECT_UEVENT`) sends hot‑plug events; `tracepoints` and `kprobes` expose via `perf` and `eBPF`.
* **System daemons**  
  * `rsyslogd` / `syslog-ng` – read `/dev/log` (Unix domain socket) and implement syslog filtering/actions.  
  * `systemd-journald` – consumes `/dev/log` and the kernel’s `journal` relay; stores binary journals in `/var/log/journal/` (persistent) or `/run/systemd/journal` (volatile).  
  * `logrotate` – invoked by `/etc/cron.daily/logrotate`; reads `/etc/logrotate.conf` and files in `/etc/logrotate.d/`.
* **Utilities**  
  * `logger` – CLI to send messages to `/dev/log` (uses `syslog(3)`).  
  * `journalctl` – query tool; supports `-u`, `-p`, `--since`, `--until`, field matches (`_PID=`, `_UID=`), and output formats (`short`, `json`, `verbose`).  
  * `systemctl` – can show journal for a unit (`systemctl status <unit>`) and trigger reloads (`systemctl reload rsyslog`).  
  * `dmesg` – reads the kernel ring buffer (`/dev/kmsg`).  
  * `bpftrace` / `perf` – attach to kernel tracepoints for custom metrics.
* **Virtual filesystems for metrics**  
  * `/proc/stat` – cumulative CPU jiffies.  
  * `/proc/meminfo` – memory statistics (total, free, buffers, cached, etc.).  
  * `/sys/block/<dev>/stat` – I/O stats (reads, writes, merges, ticks).  
  * `/sys/class/net/<if>/statistics/` – tx/rx bytes, packets, errors.  
  * `/sys/fs/cgroup/` – hierarchical resource controllers (cpu, memory, io, etc.) useful for containerised workloads.
* **Exporters** – `prometheus-node-exporter` scrapes the above files and exposes via HTTP on port 9100; `prometheus-process-exporter` provides per‑process metrics.
* **Configuration files** (representative paths)  
  * `/etc/rsyslog.conf` – main rsyslog config.  
  * `/etc/logrotate.conf` + `/etc/logrotate.d/` – per‑application rotation policies.  
  * `/etc/systemd/journald.conf` – journal size/retention settings (`SystemMaxUse=`, `MaxRetentionSec=`).  
  * `/etc/prometheus/node_exporter/` – flags for enabling/disabling collectors.

**Runnable examples**

```bash
# 1. Send a test message with specific facility/severity
logger -p local0.notice "Test local0 notice"

# 2. View the message via rsyslog (assuming a rule local0.* /var/log/local0.log)
sudo tail -n 5 /var/log/local0.log

# 3. Query the journal for the same message (journald also receives it)
journalctl _SYSTEMD_FAVORITE_PATH=/dev/log -p notice -n 5

# 4. Check current journal usage
journalctl --disk-usage

# 5. Set journal to retain at most 2GB and purge older than 7 days
sudo mkdir -p /etc/systemd/journald.conf.d
echo -e '[Journal]\nSystemMaxUse=2G\nMaxRetentionSec=7d' | sudo tee /etc/systemd/journald.conf.d/custom.conf
sudo systemctl restart systemd-journald

# 6. Rotate a custom log with size-based policy
sudo mkdir -p /var/log/myapp
echo -e '/var/log/myapp/myapp.log {\n    size 200M\n    rotate 3\n    compress\n    delaycompress\n    create 0640 myadm myadm\n    postrotate\n        systemctl kill -s HUP myapp.service >/dev/null 2>&1\n    endscript\n}' | sudo tee /etc/logrotate.d/myapp
sudo logrotate -f /etc/logrotate.d/myapp   # test rotation now
```

These snippets illustrate how the abstract concepts map to concrete filesystem paths, daemon commands, and configuration syntax on a modern Linux distribution.

## Why This Matters
Logging and observability are not ancillary chores; they are the **foundational feedback loops** that let operators infer system health, detect anomalies, and satisfy compliance. By understanding the **first‑principles**—how a `syscall` becomes a datagram on `/dev/log`, how PRI encodes facility and severity, how binary journals achieve O(log N) lookup, and how log rotation bounds disk usage—administrators can:

* **Design reliable pipelines** that route critical alerts to the right destinations without drowning in noise.  
* **Predict resource consumption** (disk, I/O, CPU) from measurable rates and configure retention/size limits proactively.  
* **Diagnose failures** quickly using indexed journal queries instead of grepping gigabytes of flat files.  
* **Instrument custom observability** via eBPF or exporters, extending the built‑in metrics with application‑specific signals.  
* **Avoid costly mistakes**—such as silent log loss after rotation or misrouted messages—that undermine trust in monitoring data.

When these pieces are correctly assembled, Linux transforms from a black box into a **transparent, observable system** where every event can be traced, measured, and acted upon, ensuring the reliability, security, and performance demanded of modern infrastructure.
