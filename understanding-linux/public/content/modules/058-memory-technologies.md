## Why This Matters

Every abstraction your program relies on — variables, arrays, the stack, mapped files — ultimately lands on physical storage built from one of a handful of semiconductor technologies. Each has radically different speed, cost, persistence, and failure characteristics that are *not* abstracted away cleanly. When a database's write-ahead log wears out SSD blocks prematurely, that is a NAND endurance problem caused by the FTL's write amplification, not a software bug. When your CPU fetches an instruction in under a nanosecond, that is an SRAM bistable latch doing its job three cache levels away from DRAM. These technologies impose hard physical constraints that propagate upward into kernel design, filesystem behavior, and application performance models. Knowing the physics lets you reason about failure modes from first principles.

## Core Concepts

### SRAM — Static Random-Access Memory

SRAM stores a bit using a **bistable latch**: six transistors (in the standard 6T cell) arranged as two cross-coupled CMOS inverters with two access transistors. The feedback loop actively fights any perturbation — if the stored value drifts, the inverter pair restores it. No external refresh is needed because the state is continuously regenerated by the circuit itself. That is what *static* means physically.

**Why it is fast and expensive:** The 6T cell is large — roughly 50–120 F² per bit (where F is the minimum feature size), versus ~6 F² for a DRAM cell. More transistors means lower density, higher leakage current, and higher manufacturing cost per bit. Access time is 0.5–5 ns. SRAM is used exclusively where speed dominates density: CPU registers, L1/L2/L3 caches. An L1 cache hit costs ~4 cycles; missing to DRAM costs ~200 cycles on a modern core. The entire cache hierarchy exists to bridge that gap.

### DRAM — Dynamic Random-Access Memory

DRAM stores a bit as a charge on a **capacitor** gated by a single transistor (1T1C cell). The capacitor holds roughly 10–30 fF of charge. This density advantage — packing a bit into one transistor instead of six — is why main memory is made from DRAM.

**Why it needs refresh:** The capacitor leaks through the transistor's off-state current and through the dielectric. A cell storing a logical `1` loses charge and can fall below the sense amplifier's decision threshold in 32–64 ms. The memory controller must issue a `REFRESH` command that activates each row, reads the charge through the sense amplifiers, and rewrites it — every row, every 64 ms (the standard `tREFI` interval). On a 16 Gb DRAM with 64K rows, a refresh command issues every ~7.8 µs. During refresh, that bank is unavailable — this is a real source of latency jitter in latency-sensitive workloads.

**Why the cache hierarchy's math is unforgiving:**

$$\text{Effective access time} = h \cdot t_{\text{hit}} + (1 - h) \cdot t_{\text{miss}}$$

With $t_{\text{hit}} = 1\,\text{ns}$ (L1 SRAM) and $t_{\text{miss}} = 100\,\text{ns}$ (DRAM), and a miss rate of $h = 0.99$:

$$t_{\text{eff}} = 0.99 \times 1 + 0.01 \times 100 = 1.99\,\text{ns}$$

A 1% miss rate doubles effective memory latency. At 5% miss rate:

$$t_{\text{eff}} = 0.95 \times 1 + 0.05 \times 100 = 5.95\,\text{ns}$$

Nearly a 6× slowdown. Cache hit rates must be ≥99% for the hierarchy to deliver near-SRAM performance. This is why spatial and temporal locality in your data structures are not optional optimizations.

### ROM and Its Variants

True **ROM** encodes bits as physical circuit topology — a bit cell either has a connection between the word line and bit line (1) or does not (0), determined at mask fabrication. There are no transistor gates to wear out; the information is structural. This is why mask ROM is used in microcontrollers for fixed boot code: it is radiation-tolerant, has effectively infinite endurance, and costs nothing at read time.

**EEPROM** replaces the physical connection with a floating-gate transistor whose threshold voltage encodes the bit. Erasing a byte applies ~12V to tunnel electrons off the floating gate. Each cell can typically sustain ~100,000 erase cycles before oxide damage causes retention failure. EEPROM is still used for small, byte-addressable nonvolatile storage: BIOS/UEFI configuration, cryptographic key material, hardware serial numbers.

### Flash Memory — NAND and NOR

Flash is EEPROM redesigned for density and cost. A floating-gate transistor has a second gate — the **floating gate** — embedded in the oxide stack between the control gate and channel. Electrons tunneled onto the floating gate via Fowler-Nordheim tunneling shift the transistor's threshold voltage $V_T$ upward; removing them shifts it back down. The control gate voltage required to turn the transistor on encodes the stored value.

In **multi-level cell** variants (MLC, TLC, QLC), the threshold voltage is divided into $2^n$ windows to store $n$ bits per cell:

$$\Delta V_T = \frac{V_{T,\text{max}} - V_{T,\text{min}}}{2^n}$$

Narrower windows mean smaller noise margins, more sensitive reads, and faster oxide degradation — which is why TLC/QLC have drastically lower endurance than SLC.

**NOR flash** connects cells in parallel: any cell can be addressed individually, read in random-access fashion, and executed directly by a CPU (XIP — eXecute In Place). Used for firmware images in embedded systems and SoCs where the bootloader must run before RAM is initialized.

**NAND flash** connects cells in series strings of 32–128 cells. The series connection eliminates per-cell select transistors, pushing density higher and cost per bit lower. The tradeoff: you cannot address individual bytes cheaply. All SSDs, eMMC, SD cards, and USB storage use NAND.

**Write endurance is a first-class design constraint:**

| Flash type | Bits/cell | Typical P/E cycle limit |
|---|---|---|
| SLC | 1 | ~100,000 |
| MLC | 2 | ~3,000–10,000 |
| TLC | 3 | ~300–1,000 |
| QLC | 4 | ~100–300 |

A consumer TLC SSD rated for 300 P/E cycles on a 1 TB drive with a write amplification factor of 3× has a total bytes written (TBW) endurance of roughly:

$$\text{TBW} = \frac{\text{capacity} \times \text{P/E cycles}}{\text{WAF}} = \frac{1000\,\text{GB} \times 300}{3} = 100\,\text{TB}$$

This is why NVMe SSDs have published TBW ratings and why databases that fsync on every transaction should be characterized against the device's WAF, not just its sequential throughput.

### Wear Leveling and the Flash Translation Layer

NAND imposes two constraints the OS block layer cannot handle directly: (1) erase granularity is a *block* (~256 KB–4 MB) while write granularity is a *page* (~4–16 KB), and (2) cells wear out. The **Flash Translation Layer (FTL)** running on the SSD's ARM controller handles both by:

1. Maintaining a **logical-to-physical page map (L2P table)** — when the OS writes LBA 0x1000, the FTL writes to a free physical page and updates the map. The old physical location is marked invalid.
2. **Garbage collection** — when a physical block has enough invalid pages, the FTL copies valid pages elsewhere and erases the block.
3. **Wear leveling** — the FTL distributes erase operations across blocks to equalize wear counts, including *static wear leveling* that moves cold data off heavily-used blocks.

The FTL's garbage collection is the primary source of **write amplification**: writing 4 KB of user data may require copying and erasing a 4 MB block, making the actual flash writes 1000× larger. Under sustained random 4K writes, WAF of 3–10× is common on consumer drives.

### Persistent Memory (NVDIMM / PMem)

Persistent memory occupies DIMM slots and is accessed via load/store instructions — no block I/O, no DMA, no 4K page round-trips. Intel Optane DCPMM (based on 3D XPoint) had ~300 ns read latency and ~100 ns write latency, versus ~80 ns for DDR4 and ~100 µs for NVMe SSD reads. It retained data across power loss.

This breaks the foundational assumption of the POSIX storage model: that byte-addressability implies volatility and persistence implies block I/O. With PMem, a 64-byte cache line write that is flushed with `CLWB` and followed by `SFENCE` is a durable, byte-granular persistent write — no filesystem write path required. This forces a new class of bugs: **torn writes** across cache-line boundaries that survive reboots, because the CPU may have written only some cache lines before a crash. Databases targeting PMem must use 8-byte atomic stores (which are guaranteed torn-write-free on x86) as their durability primitive, not `write(2)`.
