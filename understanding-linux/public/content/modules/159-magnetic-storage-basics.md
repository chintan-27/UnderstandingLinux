## Why This Matters

When a process calls `read()`, the VFS layer, page cache, block layer, and device driver all intervene before any physical I/O happens. But when the page cache misses and a real disk read is required, the performance is governed by mechanics: a spinning platter, a moving arm, and the laws of rotational inertia. A 7200 RPM HDD delivers roughly 80–120 random IOPS. A modern NVMe SSD delivers 500,000+. That four-orders-of-magnitude gap is not a software problem — it is geometry. Understanding the geometry tells you why the Linux block layer exists, what the I/O scheduler actually does, why `ext4` and `XFS` lay out data the way they do, and why a single random-read workload can saturate a disk that handles sequential reads trivially.

## Core Concepts

### Platters, Tracks, and Sectors

An HDD stores bits by magnetizing regions of an iron-oxide-coated platter. Each region's polarity encodes a 0 or 1. The platter spins continuously; data is arranged in concentric rings called **tracks**. Each track is divided into fixed-size **sectors** — the smallest addressable unit. The traditional sector size is 512 bytes; drives since ~2010 use **Advanced Format** with 4096-byte physical sectors (often emulating 512-byte logical sectors for compatibility, called 512e).

The read/write head floats roughly 3–5 nanometers above the platter surface on an air bearing generated by the platter's rotation. Contact means catastrophic failure — a **head crash**. Multiple platters share a spindle; the set of tracks at the same radial position across all platters forms a **cylinder**. A single seek moves all heads simultaneously, so reading from the same cylinder on multiple platters requires no additional seek.

Sector size affects addressing. The kernel reports logical sector size via:

```bash
cat /sys/block/sda/queue/logical_block_size   # typically 512
cat /sys/block/sda/queue/physical_block_size  # typically 4096 on AF drives
```

A mismatch between partition alignment and physical sector boundaries causes every logical write to require a read-modify-write cycle, degrading write performance silently.

### Seek Time

Moving the arm radially to the target track is a **seek**. It dominates random I/O cost because it involves accelerating and decelerating a physical mass. Seek time is not constant — it scales (roughly) with distance:

$$T_{seek}(c_1, c_2) = T_{min} + (T_{max} - T_{min}) \cdot \frac{|c_1 - c_2|}{C}$$

where $C$ is the total cylinder count, $T_{min} \approx 0.2\text{ ms}$ (adjacent track), and $T_{max} \approx 15\text{–}20\text{ ms}$ (full stroke). For uniformly random I/O, the expected seek distance is $C/3$, giving:

$$E[T_{seek}] = T_{min} + \frac{T_{max} - T_{min}}{3} \approx \frac{T_{max}}{3}$$

This is why drive specs quote average seek ~7 ms when maximum is ~20 ms — it is the statistical expectation over a uniform distribution, not a measurement of any specific access.

### Rotational Latency

After the seek, the correct sector must rotate under the head. The platter doesn't stop; if the target sector just passed, you wait nearly a full revolution. The full rotation period at $N$ RPM:

$$T_{rotation} = \frac{60}{N} \text{ s}$$

Expected rotational latency (uniform distribution of sector positions):

$$E[T_{latency}] = \frac{T_{rotation}}{2} = \frac{30}{N} \text{ s}$$

At 7200 RPM: $E[T_{latency}] = 30/7200 \approx 4.17\text{ ms}$

At 5400 RPM (common in laptops): $E[T_{latency}] = 30/5400 \approx 5.56\text{ ms}$

The implication: a slower spindle speed hurts random I/O disproportionately because rotational latency adds directly to every random access, compounding the seek penalty.

### Transfer Time

Once the head is positioned, data transfer is just reading bits as sectors sweep past. For a single 4 KB sector on a drive with 150 MB/s sequential throughput:

$$T_{transfer} = \frac{4096 \text{ B}}{150 \times 10^6 \text{ B/s}} \approx 0.027 \text{ ms}$$

Transfer time is negligible for small reads. It matters only for large sequential transfers, where seek and rotational latency are amortized across many sectors.

### Total Random I/O Time and IOPS Ceiling

$$T_{IO} = T_{seek} + T_{latency} + T_{transfer}$$

For a 7200 RPM HDD with average seek 7 ms:

$$T_{IO} \approx 7 + 4.17 + 0.03 \approx 11.2 \text{ ms}$$

Maximum sustainable random IOPS:

$$\text{IOPS}_{max} = \frac{1}{T_{IO}} = \frac{1}{0.0112} \approx 89 \text{ IOPS}$$

This is a hard ceiling imposed by physics, not firmware. No driver optimization, no queue depth tuning, no filesystem tweak will push a single 7200 RPM HDD past ~120 random IOPS for small reads. The only levers are: increase queue depth to pipeline requests (limited by rotational geometry), use larger I/Os to amortize latency, or eliminate random I/O entirely.

### Why Sequential Access Dominates

Sequential reads eliminate both major cost components. The head stays near the current track (adjacent-track seeks cost ~0.2 ms), and sectors arrive in order with no rotational wait — the drive reads them as fast as they pass. The result:

$$\frac{\text{Sequential throughput}}{\text{Random throughput}} = \frac{150 \text{ MB/s}}{89 \text{ IOPS} \times 4 \text{ KB}} = \frac{150 \text{ MB/s}}{0.35 \text{ MB/s}} \approx 430\times$$

This ratio is why databases use append-only write-ahead logs (WAL): converting random updates into sequential log appends turns a 89 IOPS operation into a 150 MB/s operation on the same hardware. It is also why SSDs change database architecture — their random-vs-sequential ratio is close to 1, eliminating the primary motivation for WAL-style indirection.

## How It Works

### The Access Pattern Problem in Numbers

For 10,000 random 4 KB reads on a 7200 RPM HDD:

$$T_{total} = 10{,}000 \times 11.2 \text{ ms} = 112 \text{ seconds}$$

For 10,000 sequential 4 KB reads at 150 MB/s:

$$T_{total} = \frac{10{,}000 \times 4096 \text{ B}}{150 \times 10^6 \text{ B/s}} \approx 0.27 \text{ seconds}$$

This 415× difference is not workload-specific — it is the physics of the device. It explains why:
- Databases (InnoDB, PostgreSQL) maintain buffer pools: a cache hit costs ~100 ns; a miss costs ~11 ms — a 110,000× penalty.
- `ext4` and `XFS` use delayed allocation: accumulating writes in memory and flushing in large sequential batches rather than writing each `write()` syscall immediately.
- `hdparm -t` (sequential) and `hdparm -T` (cache) benchmarks show radically different numbers for the same drive.

### The I/O Scheduler: Reordering to Minimize Seek Distance

When multiple processes issue random I/O simultaneously, servicing requests in arrival order causes the arm to oscillate across the disk — the **seek storm**. The kernel's block layer reorders requests before issuing them to the driver.

The **elevator (SCAN) algorithm** sweeps the arm in one direction, servicing all queued requests at tracks it passes, then reverses. Worst-case seek is bounded to one full disk sweep rather than $O(n \times C)$ for $n$ random requests.

Linux's **deadline** scheduler (the traditional choice for HDDs) adds per-request deadlines to prevent starvation:
- Read deadline: 500 ms (default)
- Write deadline: 5000 ms (default)
- Separate read and write queues; reads are prioritized because processes typically block on reads but not writes

**mq-deadline** is the multi-queue variant for modern kernels (5.x+). **BFQ** (Budget Fair Queuing) is preferred when interactive latency matters — it tracks I/O budgets per process group and avoids starving interactive applications behind bulk writes.

Check and change the scheduler:

```bash
# View current scheduler for a device
cat /sys/block/sda/queue/scheduler
# Output: mq-deadline [bfq] none  (brackets indicate active)

# Change to mq-deadline for an HDD
echo mq-deadline | sudo tee /sys/block/sda/queue/scheduler

# Verify
cat /sys/block/sda/queue/scheduler
# Output: [mq-deadline] bfq none

# Check read/write deadline values (in ms)
cat /sys/block/sda/queue/iosched/read_expire
cat /sys/block/sda/queue/iosched/write_expire
```

For SSDs and NVMe, I/O scheduling adds latency without benefit (no seek cost to optimize), so `none` is appropriate:

```bash
echo none | sudo tee /sys/block/nvme0n1/queue/scheduler
```
