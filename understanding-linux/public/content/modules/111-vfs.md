## Core Concepts
### Introduction to VFS
The Virtual File System (VFS) is the kernel’s abstraction layer that translates VFS‑independent system call semantics (`open(2)`, `read(2)`, `stat(2)`, …) into filesystem‑specific operations. Its purpose is two‑fold:  

1. **Interface uniformity** – user‑space sees a single set of calls regardless of whether the underlying storage is ext4, XFS, tmpfs, NFS, or a FUSE daemon.  
2. **Resource sharing** – the VFS caches metadata (dentries, inodes, superblocks) so that repeated accesses to the same file avoid costly disk I/O.

The VFS sits between the **system call entry point** (`sys_open` → `do_sys_open` → `do_filp_open`) and the **filesystem’s method tables** (`struct inode_operations`, `struct file_operations`, `struct super_operations`). When a syscall invokes a VFS function, the VFS looks up the appropriate object (dentry → inode → superblock) and forwards the call to the low‑level filesystem’s implementation via function pointers.

### Dentries
A **dentry** (`struct dentry`) represents a *name‑to‑inode* binding within a directory. It is **not** permanent storage; it is a transient object that lives in the **dcache** (dentry cache). Key fields:

| Field | Meaning | Typical size (bytes) |
|-------|---------|----------------------|
| `d_name` | `struct qstr { unsigned len; const char *name; }` – the filename component | 2·sizeof(void*) + len |
| `d_inode` | Pointer to the associated `struct inode` (or `NULL` for a negative dentry) | 8 |
| `d_parent` | Pointer to the parent directory’s dentry | 8 |
| `d_subdirs` | `struct list_head` of child dentries (used for walking a directory) | 16 |
| `d_rcu` | RCU head for lock‑free lookups | 16 |
| `d_count` | Atomic reference count (`atomic_t`) | 4 |
| `d_flags` | Bit‑field (e.g., `DCACHE_REFERENCED`, `DCACHE_LRU_LIST`) | 4 |
| `d_lru` | `struct list_head` for LRU lists (used / unused) | 16 |
| `d_hash` | `struct hlist_node` for hash‑table linkage | 16 |
| `d_op` | Pointer to `struct dentry_operations` (filesystem‑specific ops) | 8 |
| `d_fsdata` | Private data pointer for the filesystem | 8 |
| … | (padding, lockseqlock, etc.) | ~24 |

Total ≈ **192 bytes** on x86‑64 (including padding).  

The dcache is organized for **O(1)** average lookup:

* A **hash table** (`dentry_hashtable`) of size `2^k` buckets.  
* Hash function: `hash = dentry_hash(parent_dentry, name) = jhash2(name, len, seed) ^ (unsigned long)parent_dentry`.  
* Expected chain length = load factor `α = n / m` (`n` dentries, `m` buckets). With the default `dentry_hashtable` size tuned to `nr_dentries / 4`, `α ≈ 0.25`, giving < 1.33 steps per lookup on average.

Negative dentries (name‑lookup that failed) are also cached to avoid repeated failed lookups; they have `d_inode == NULL` and are kept on the **LRU list** for reclamation.

### Inodes
An **inode** (`struct inode`) stores the *metadata* of a filesystem object (file, directory, symlink, device, …). It is the on‑disk counterpart that the VFS caches in the **icache**. Important fields (simplified):

| Field | Meaning |
|-------|---------|
| `i_ino` | Inode number (unique within the filesystem) |
| `i_mode` | File type + permission bits (`S_IFMT | S_IRWXU …`) |
| `i_uid`, `i_gid` | Ownership |
| `i_nlink` | Number of hard links (directory entries pointing to this inode) |
| `i_size` | File length in bytes (for regular files) |
| `i_atime`, `i_mtime`, `i_ctime` | Timestamps (timespec64) |
| `i_op` | Pointer to `struct inode_operations` (e.g., `create`, `lookup`, `unlink`) |
| `i_fop` | Pointer to `struct file_operations` (default file ops) |
| `i_sb` | Back‑pointer to the owning `struct super_block` |
| `i_mapping` | `struct address_space *` for page‑cache management |
| `i_flags`, `i_state` | Bit‑fields for locking, dirty, reclaim state |
| … | RCU head, lockseqlock, etc. |

Typical size: **≈ 512 bytes** (varies with filesystem).  

The VFS maintains **per‑superblock inode hash tables** (`inode_hashtable`) for quick `iget`/`iput` lookups, using the same hash‑table principle as dentries.

### Superblocks
A **superblock** (`struct super_block`) describes a mounted filesystem instance. It holds global parameters:

* `s_blocksize`, `s_blocksize_bits` – fundamental I/O unit.
* `s_magic` – filesystem identifier (e.g., `EXT4_SUPER_MAGIC`).
* `s_type` – pointer to `struct file_system_type` (holds name, mount, kill_sb).
* `s_root` – dentry of the filesystem’s root (`/`).
* `s_fs_info` – private data pointer (e.g., `ext4_sb_info`).
* `s_dev` – `dev_t` of the underlying block device.
* `s_flags` – mount flags (`MS_RDONLY`, `MS_NOEXEC`, …).
* `s_time_gran` – timestamp resolution (nanoseconds for modern FS).

The superblock is read from disk during `mount` and cached; modifications (e.g., `sync`) write back the dirty fields via `super_operations->sync_fs`.

### File Objects
A **file object** (`struct file`) represents an *open file description* (the kernel side of a file descriptor). It is **not** per‑process; multiple descriptors can refer to the same `struct file` (dup, fork). Key members:

| Field | Meaning |
|-------|---------|
| `f_path` | `struct path { struct dentry *dentry; struct vfsmount *mnt; }` – the dentry+vfsmount pair |
| `f_inode` | Shortcut to `dentry->d_inode` |
| `f_op` | Pointer to `struct file_operations` (read, write, llseek, …) |
| `f_flags` | Open flags (`O_RDONLY`, `O_APPEND`, …) copied from `open(2)` |
| `f_pos` | 64‑bit file offset (updated on each read/write) |
| `f_count` | Atomic reference count (`atomic_t`) |
| `f_version` | Used for `struct file` validation under `fcntl(F_GETFL)` |
| `f_ra` | `struct file_ra_state` for read‑ahead heuristics |
| … | RCU head, lock, etc. |

Size ≈ **144 bytes**.  

When a process calls `open(2)`, the VFS:

1. Allocates a new `struct file` via `get_empty_filp()`.
2. Sets `f_path.dentry` to the resolved dentry, `f_path.mnt` to the mount point’s `vfsmount`.
3. Copies `open(2)` flags into `f_flags`.
4. Calls `f_op->open(inode, file)` (often `generic_file_open`), which may increment `i_count` and set up private data.
5. Installs the `struct file*` into the process’s file descriptor table (`fd_install(fd, file)`).

The **file descriptor table** is an array of pointers (`struct fdtable`); each entry holds a `struct file*` and flag bits (`FD_CLOEXEC`).

## How It Works
### Path Resolution → Dentry Lookup
When a syscall supplies a pathname (e.g., `/home/user/file.txt`), the VFS performs **lookup** in three phases:

1. **Mount namespace resolution** – find the `vfsmount` that contains the path’s prefix (using `current->nsproxy->mnt_ns`).  
2. **Component‑by‑component walk** – for each pathname component `name_i`:
   * Compute hash `h = hash(dentry_parent, name_i)`.  
   * Scan the bucket `dentry_hashtable[h]` for a dentry with matching `d_parent` and `d_name`.  
   * If found and `d_count > 0`, use it (rcu‑read lock ensures the dentry won’t disappear).  
   * If not found or negative, invoke the filesystem’s `lookup` inode operation (`parent->i_op->lookup`) to create a new dentry (`d_alloc`, `d_instantiate`).  
   * On success, increment the dentry’s refcount (`dget`) and continue.
3. **Final dentry** – after processing the last component, we have a dentry representing the target (file, directory, symlink, etc.).  

If any component is a symlink, the VFS follows it (up to `MAXSYMLINKS` = 40) by re‑starting walk from the link’s target, preserving the remaining suffix.

### Inode Retrieval & Caching
Once we have the target dentry, the VFS accesses its inode via `dentry->d_inode`. The inode may already be in the **icache**; if not, `iget5_locked` allocates a new `struct inode`, reads the on‑disk inode (via the filesystem’s `read_inode` op), inserts it into the per‑superblock hash table, and marks it `I_NEW`.  

The VFS protects concurrent access with:

* **`i_lock`** (rw_semaphore) for modifications that change `i_mode`, `i_nlink`, `i_size`, etc.  
* **`i_rwsem`** (lockdep class) for file‑size truncation and page‑cache operations.  
* **RCU** for dentry lookups (readers hold `rcu_read_lock()`; updates use `call_rcu` to free after a grace period).  

Thus, a path lookup is **largely lock‑free**; only when a new dentry/inode must be created do we take the appropriate locks.

### Caching Hierarchy & Performance
The VFS employs three main caches, each backed by a **slab allocator**:

| Cache | Backing slab | Typical object size | Approx. # objects (system with 8 GB RAM) |
|-------|--------------|---------------------|------------------------------------------|
| dentry cache (`dcache`) | `kmem_cache_create("dentry", …)` | 192 B | ~ 20 M |
| inode cache (`icache`)  | `kmem_cache_create("inode", …)` | 512 B | ~ 8 M |
| file cache (`filp`)    | `kmem_cache_create("filp", …)` | 144 B | ~ 30 M |

Each cache maintains **LRU lists** (`shrink_dcache_memory`, `shrink_icache_memory`) that the VMS calls under memory pressure. Objects with a refcount of zero are candidates for reclamation; negative dentries are preferentially reclaimed.

The **expected cost** of a cached lookup (assuming the dentry is hot) is:

\[
T_{\text{lookup}} \approx T_{\text{hash}} + T_{\text{cmp}} \approx O(1) + O(\text{len(name)})
\]

where `T_hash` is a few CPU cycles (Jenkins hash) and `T_cmp` is `strcmp` on the name (usually < 10 bytes).  

If the dentry is missing, we incur a **filesystem lookup** (`lookup` inode op), which may involve:

* Reading a directory block from the block device (typically 4 KB).  
* Parsing the directory entries (extent‑based or linear).  
* Allocating and initializing a new dentry/inode (slab allocation + zero‑fill).  

On a SSD with 100 µs read latency, a cold lookup adds ~ 100 µs; on HDD (~ 8 ms) it dominates. Hence, the dcache hit ratio directly impacts I/O latency.

### Example Flow: `open("/etc/passwd", O_RDONLY)`
1. **Mount ns** → root mount (`/`).  
2. **Component “etc”** → hash lookup in root dentry’s dcache → found, `dget`.  
3. **Component “passwd”** → hash lookup in `etc` dentry → **miss** → call `ext4_lookup` (or whichever FS).  
   * Reads the directory block for `/etc`.  
   * Finds the entry, allocates a new dentry (`d_alloc`) and inode (`iget`).  
   * Sets `dentry->d_inode = inode`, increments both refcounts.  
4. **Allocate file object** (`get_empty_filp`).  
5. **Set** `f_path.dentry = dentry`, `f_path.mnt = mnt`, `f_flags = O_RDONLY`.  
6. **Call** `f_op->open` → `generic_file_open` (increments `i_count`).  
7. **Return** the new fd to userspace.  

If the file is later opened again by the same or another process, steps 2‑3 hit the dcache/icache, eliminating the disk read.

## Worked Examples
### Example 1: Creating a New Regular File (`creat("/tmp/foo", 0644)`)
We trace the VFS calls from `sys_creat` → `do_sys_open` → `do_filp_open` with flags `O_CREAT|O_WRONLY|O_TRUNC`.

| Step | Action | Kernel function | Key details |
|------|--------|------------------|-------------|
| 1 | Path resolution for `/tmp/foo` | `filename_lookup` (same as lookup) | Resolves `/tmp` (existing) → dentry `tmp_dentry`. For final component `foo`: hash miss → call `tmp_dir->i_op->lookup`. |
| 2 | Allocate new dentry | `d_alloc(tmp_dentry, &qstr foo)` | Returns `dentry_foo` with `d_count=1`, `d_inode=NULL`. |
| 3 | Allocate new inode | `new_inode(tmp_dentry->d_sb)` | Allocates from icache, sets `i_mode = S_IFREG | 0644`, `i_uid = current_fsuid()`, `i_gid = current_fsgid()`, `i_nlink = 1`. |
| 4 | Link dentry↔inode | `d_instantiate(dentry_foo, inode)` | Sets `dentry_foo->d_inode = inode`, `inode->i_dentry = dentry_foo` (via `SB_I_COPYUP` if needed). |
| 5 | Update parent directory | `tmp_dir->i_op->create(inode_dir, dentry_foo, mode, &nd)` (usually `ext4_create`) | * Allocates an on‑disk inode for `foo`.<br>* Writes a directory entry (name `foo`, inode number) into `/tmp`’s directory block.<br>* Increments `tmp_dir->i_size` by the directory entry length.<br>* Marks parent inode dirty (`mark_inode_dirty(tmp_dir)`). |
| 6 | Open file for writing | `struct file *file = get_empty_filp();`<br>`file->f_path.dentry = dentry_foo;`<br>`file->f_path.mnt = mnt_tmp;`<br>`file->f_flags = O_WRONLY|O_CREAT|O_TRUNC;`<br>`file->f_op = &def_file_fops;`<br>`inode->i_op->open(inode, file);` | `def_file_fops.open` = `generic_file_open` → increments `inode->i_count`. |
| 7 | Install fd | `fd_install(fd, file);` | Returns fd to userspace. |
| 8 | Cleanup on error (if any) | `iput(inode)`, `dput(dentry_foo)` | Ensures refcounts are balanced. |

**Result:** A new regular file appears on disk with mode `0644`, one hard link (`i_nlink=1`), and an empty size. The dentry and inode are now hot in their respective caches; subsequent `stat("/tmp/foo")` hits the dcache/icache directly.

### Example 2: Reading 4096 Bytes from a File (`pread(fd, buf, 4096, 0)`)
Assume the file is already open (`fd` points to `struct file *filp`) and its inode’s `i_size >= 4096`.

| Step | Action | Kernel function | Details |
|------|--------|------------------|---------|
| 1 | Validate fd & flags | `fget_light(fd)` | Increments `filp->f_count` atomically; checks `filp->f_mode & FMODE_READ`. |
| 2 | Compute offset & length | `loff_t pos = filp->f_pos;` (if `pread` supplied offset, use that) | No modification of `filp->f_pos` for `pread`. |
| 3 | Call VFS read | `vfs_read(filp, buf, 4096, &pos);` | `vfs_read` does: <br>• `if (!filp->f_op->read) return generic_file_read_iter(filp, ...);` <br>• For most FS, `generic_file_read_iter` invokes `generic_file_read_iter` → `generic_file_read_iter` → `call_read_iter(filp->f_op->read_iter, ...)`; many FS set `read_iter = generic_file_read_iter`. |
| 4 | Page‑cache lookup | `filemap_read(filp->f_mapping, pos, 4096, &flags)` | * Looks for pages covering `[pos, pos+4096)` in the page cache via `find_get_pages`. <br>• If a page is missing, triggers `readahead` and `submit_bh` to read the underlying block(s) from the block device. |
| 5 | Copy to userspace | `copy_to_user(buf, page_address, len)` | Uses `kmapped` or `kmap_atomic` if needed; otherwise direct memcpy if page is already kmapped. |
| 6 | Update file position (only for `read`, not `pread`) | N/A | For `pread`, `filp->f_pos` stays unchanged. |
| 7 | Release fd ref | `fput_light(filp)` | Decrements `filp->f_count`; if zero, calls `filp->f_op->release`. |

**Timing estimate (SSD, hot page cache):**  
- Page‑cache hit: `~ 150 ns` (TLB + memcpy).  
- Miss (needs disk): SSD read latency `~ 100 µs` + overhead `~ 5 µs` → `~ 105 µs`.  
Thus, if the file’s first 4 KB is cached, the syscall costs sub‑microsecond; otherwise it’s dominated by storage latency.

### Example 3: Deleting a File (`unlink("/tmp/foo")`)
We follow `sys_unlinkat` → `do_unlinkat` → `vfs_unlink`.

| Step | Action | Kernel function | Details |
|------|--------|------------------|---------|
| 1 | Path resolution for `/tmp/foo` (parent = `/tmp`, name = `foo`) | Same as lookup, but **stop before final component** – we obtain `parent_dentry` (`/tmp`) and the target dentry (`target_dentry`). |
| 2 | Ensure target is not a directory | `if (d_is_dir(target_dentry)) return -EISDIR;` |
| 3 | Obtain inode | `inode = target_dentry->d_inode;` |
| 4 | Check write permission on parent | `if (!inode_owner_or_capable(parent_dentry->d_inode)) return -EACCES;` (actually checks `parent_inode->i_op->permission`). |
| 5 | Call filesystem’s unlink op | `int ret = parent_dentry->d_inode->i_op->unlink(parent_dentry->d_inode, target_dentry);` (e.g., `ext4_unlink`). |
|    | Inside `ext4_unlink`: | | * Decrement the target inode’s `i_nlink`.<br>* If `i_nlink` reaches zero: <br> - Call `truncate_inode_pages(inode, 0)` to drop any cached pages.<br> - Call `clear_inode(inode)` → frees on‑disk inode, updates block bitmap.<br> - Call `delete_inode(inode)` → finalizes icache removal (`iput` later).<br>* Remove the directory entry from the parent’s directory block (modify the block, update `i_size`).<br>* Mark parent inode dirty (`mark_inode_dirty(parent_inode)`). |
| 6 | Update VFS state | `d_drop(target_dentry);` – makes the dentry **negative** (sets `d_inode = NULL`) but keeps it in dcache for negative caching. |
| 7 | Decrement refcounts | `dput(target_dentry);` (drops the dentry ref we got from lookup).<br>`iput(inode);` (drops the inode ref). |
| 8 | Return status to userspace | `return ret;` (0 on success). |

**Why we keep a negative dentry:**  
If a process later calls `open("/tmp/foo")`, the VFS will find the negative dentry, see `d_inode == NULL`, and **immediately return `-ENOENT`** without hitting the underlying filesystem, saving a disk read. The negative dentry stays in the dcache until memory pressure reclaims it.

## Common Mistakes
### Mistake 1: Assuming `dentry->d_inode` Is Always Valid
**What’s wrong:**  
Code such as `if (dentry->d_inode->i_mode & S_IFREG) …` without checking for `NULL` can dereference a negative dentry, causing an OOPS.

**Why it happens:**  
After an `unlink` or `rmdir`, the VFS calls `d_drop(dentry)` which clears `d_inode` but leaves the dentry in the dcache (negative caching). If the code retains a pointer to that dentry (e.g., from a prior lookup) and later checks the inode, it sees a stale pointer.

**How to avoid:**  
* Use `d_is_positive(dentry)` macro (`
