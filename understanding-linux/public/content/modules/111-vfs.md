## Why This Matters

Linux mounts ext4 on spinning rust, tmpfs in RAM, NFS over a network, and procfs backed by kernel data structures — and `open()`/`read()`/`write()` works identically on all of them. This is not accidental. The VFS defines a mandatory object model: every filesystem must implement a fixed set of operations through function-pointer tables. The kernel calls `file->f_op->read()` without knowing or caring whether the backing store is a block device, a network socket, or a kernel counter that increments on access.

The alternative — no VFS — means every `read()` call contains a `switch` on filesystem type. Adding a new filesystem means patching every syscall. The VFS makes filesystems a **plugin interface**: implement the vtables, register with `register_filesystem()`, done.

## Core Concepts

### The Four Primary VFS Objects

The VFS models a filesystem using four C structures with carefully separated lifetimes and scopes:

| Object | What it represents | Lifetime |
|---|---|---|
| `super_block` | One mounted filesystem instance | mount → umount |
| `inode` | One file's metadata, filesystem-wide | until all links removed and refcount → 0 |
| `dentry` | One resolved path component, in-memory only | until evicted from dcache |
| `file` | One open-file description for one process | `open()` → `close()` |

The non-obvious separations:

- One inode, **multiple dentries**: every hard link is a separate dentry pointing to the same inode. `ln a b` creates a second dentry `b`; both share one inode. The inode has no concept of a "name" — names live entirely in dentries.
- One inode, **multiple file objects**: every independent `open()` call creates a new `struct file` with its own `f_pos`. If two processes open the same file without `dup()` or `fork()`, they each have independent seek positions. If they share via `fork()`, they share one `struct file`.

These distinctions control exactly what gets invalidated, what gets locked, and where races can occur.

### The Superblock: Filesystem-Wide Control

`struct super_block` (defined in `include/linux/fs.h`) is the kernel's in-memory representation of a mounted filesystem. It holds block size, total inode count, a pointer to the root dentry, and — decisively — a pointer to `super_operations`, the vtable the VFS dispatches through for filesystem-wide operations.

```c
struct super_operations {
    struct inode *(*alloc_inode)(struct super_block *sb);
    void (*destroy_inode)(struct inode *);
    void (*dirty_inode)(struct inode *, int flags);
    int  (*write_inode)(struct inode *, struct writeback_control *wbc);
    void (*evict_inode)(struct inode *);
    void (*put_super)(struct super_block *);
    int  (*sync_fs)(struct super_block *sb, int wait);
    int  (*freeze_fs)(struct super_block *);
    int  (*unfreeze_fs)(struct super_block *);
    int  (*statfs)(struct dentry *, struct kstatfs *);
    // ...
};
```

When you run `mount -t ext4 /dev/sda1 /mnt`, the kernel calls `ext4_fill_super()`, which reads the on-disk superblock, allocates a `struct super_block`, and sets `sb->s_op = &ext4_sops`. All subsequent VFS calls on that mount go through `ext4_sops`. A different filesystem registered under a different name does the same — the VFS never calls ext4 code directly.

`sync_fs()` and `write_inode()` are separate because they can fail independently: `sync_fs()` flushes metadata (journal commits in ext4), while `write_inode()` writes individual inode records. If `sync_fs()` succeeds but a subsequent `write_inode()` fails, the journal is consistent but the inode table may not be — the filesystem must handle this asymmetry.

### The Inode: Metadata Without a Name

The inode holds everything about a file except its name and its data content:

```c
struct inode {
    umode_t         i_mode;       // permissions + file type
    uid_t           i_uid;
    gid_t           i_gid;
    unsigned long   i_ino;        // inode number (filesystem-local)
    loff_t          i_size;       // byte count
    struct timespec i_atime, i_mtime, i_ctime;
    unsigned long   i_nlink;      // hard link count
    const struct inode_operations *i_op;
    const struct file_operations  *i_fop;
    struct super_block            *i_sb;
    struct address_space          *i_mapping; // page cache linkage
    // ...
};
```

The `inode_operations` vtable covers operations **on the file metadata** — operations where the filesystem must reach into its on-disk structures:

```c
struct inode_operations {
    struct dentry *(*lookup)(struct inode *, struct dentry *, unsigned int);
    int (*create)(struct inode *, struct dentry *, umode_t, bool);
    int (*link)(struct dentry *, struct inode *, struct dentry *);
    int (*unlink)(struct inode *, struct dentry *);
    int (*mkdir)(struct inode *, struct dentry *, umode_t);
    int (*rmdir)(struct inode *, struct dentry *);
    int (*rename)(struct inode *, struct dentry *,
                  struct inode *, struct dentry *, unsigned int);
    int (*permission)(struct inode *, int);
    int (*setattr)(struct dentry *, struct iattr *);
    int (*getattr)(const struct path *, struct kstat *, u32, unsigned int);
    // ...
};
```

`lookup()` is the critical one: given a directory inode and a name, find the child inode on disk. The VFS calls this on a dcache miss. Everything else in path resolution builds on what `lookup()` returns.

The separation of name from metadata is what makes hard links structurally inevitable rather than a bolted-on feature: the filesystem records data at inode $N$, and any number of directory entries can reference inode $N$. The link count `i_nlink` tracks this; `unlink()` decrements it, and the inode is freed only when `i_nlink == 0` **and** `i_count == 0` (no open file descriptors remain).

### The Dentry: Path Resolution Cache

A dentry maps one `(parent, name)` pair to one inode. It is **never written to disk** — it is a pure kernel memory structure whose only purpose is to avoid repeating the expensive `lookup()` call. The on-disk representation of directory entries (e.g., ext4's `ext4_dir_entry_2`) is a completely separate structure that the filesystem reads during `lookup()` and then discards into a dentry.

```c
struct dentry {
    unsigned int         d_flags;
    struct dentry       *d_parent;
    struct qstr          d_name;    // name + precomputed hash
    struct inode        *d_inode;   // NULL if negative dentry
    struct list_head     d_child;   // siblings in parent's d_subdirs
    struct list_head     d_subdirs;
    struct hlist_node    d_hash;    // slot in dcache hash table
    struct list_head     d_lru;     // position in LRU list
    atomic_t             d_count;
    const struct dentry_operations *d_op;
    struct super_block  *d_sb;
    // ...
};
```

Dentry states and their transitions:

- **Used** (`d_inode != NULL`, `d_count > 0`): actively referenced by a path walk or open file. Cannot be evicted.
- **Unused** (`d_inode != NULL`, `d_count == 0`): valid, sits on the LRU list. Will be evicted under memory pressure.
- **Negative** (`d_inode == NULL`): a confirmed non-existence. Caching this prevents repeated `lookup()` calls for names that don't exist — `stat()`-ing a missing file repeatedly is $O(1)$ instead of $O(d)$ per call where $d$ is the number of path components.

A dentry's **lookup key** is `(d_parent, d_name.hash)`. The hash table slot index is:

$$\text{slot} = \text{d\_name.hash} \bmod 2^k$$

where $2^k$ is the current dcache hash table size (power of two, grows with system RAM). Collisions are chained; the expected lookup cost is $O(1)$ under a uniform hash distribution.

### The File Object: Per-Open-Call State

`struct file` is created by `open()` and destroyed by `close()`. It is process-facing state — the things that differ between two independent opens of the same file:

```c
struct file {
    struct path         f_path;      // dentry + vfsmount
    const struct file_operations *f_op;
    loff_t              f_pos;       // current seek position
    unsigned int        f_flags;     // O_RDONLY, O_NONBLOCK, etc.
    fmode_t             f_mode;
    struct fown_struct  f_owner;     // for SIGIO/fasync
    void               *private_data; // filesystem-specific state
    struct address_space *f_mapping;
    // ...
};
```

`file_operations` is the vtable for **data-plane operations** — reading, writing, seeking, memory-mapping:

    ssize_t (*read_iter)(struct kiocb *, struct iov_iter *);
    ssize_t (*write_iter)(struct kiocb
