## Why This Matters

Processes are isolated by design — the kernel enforces separate virtual address spaces so a memory corruption bug in one process cannot silently propagate to another. But isolation creates a coordination problem: a shell must connect pipeline stages, a browser must delegate rendering to a sandboxed subprocess, a database must multiplex client connections against a shared buffer pool. Each IPC mechanism resolves this coordination problem with different guarantees about latency, ordering, persistence, and synchronization. Choosing incorrectly — or misunderstanding what a mechanism does and does not guarantee — produces race conditions, deadlocks, and silent data loss that are notoriously difficult to reproduce under a debugger.

## Core Concepts

### Pipes

A pipe is a kernel-managed circular byte buffer exposed as two file descriptors: one write end, one read end. It is strictly unidirectional. The kernel allocates a `pipe_inode_info` structure holding the ring buffer (16 pages = 64 KB by default on Linux since 2.6.11) and two wait queues. When the buffer is full, `write()` blocks on the writer wait queue; when it is empty, `read()` blocks on the reader wait queue. This blocking is the synchronization — no userspace lock is needed because the kernel serializes access inside the buffer.

Pipes exist only in kernel memory, not on disk. They survive only as long as at least one file descriptor referencing each end remains open. Because `fork()` duplicates file descriptors, parent and child inherit both ends and must close whichever end they do not use. **If any process holds the write end open, `read()` on the read end will never return 0 (EOF)** — the kernel cannot distinguish "writer will write more" from "writer is done" until all write-end file descriptors are closed. This is the most common pipe bug.

Named pipes (FIFOs) extend pipes to unrelated processes by registering a path in the VFS. The underlying buffer mechanism is identical; the difference is purely in how the two ends find each other.

### Message Queues

A message queue is a kernel-maintained priority queue of discrete, typed blobs. Unlike a pipe, it preserves **message boundaries** — `mq_send()` enqueues one atomic unit; `mq_receive()` dequeues exactly that unit. You never need to implement your own framing protocol.

The kernel orders messages by priority, not insertion time. Among equal-priority messages, ordering is FIFO. The queue lives entirely in kernel space, identified by a name (e.g., `/demo`) rather than a file descriptor tied to any process. It persists until `mq_unlink()` is called, regardless of whether any process holds it open. This persistence is deliberately useful — a producer can exit and the consumer still drains the queue — but leaked queues consume kernel memory counted against `/proc/sys/fs/mqueue/queues_max`.

### Shared Memory

Shared memory is the fastest IPC mechanism because data is never copied. The kernel maps the same physical page frames into multiple processes' page tables. A write by process A modifies the physical page directly; process B's virtual address for that page points to the same frame, so the write is visible without any system call for the transfer itself.

The cost: the kernel provides **no synchronization whatsoever**. Two processes writing concurrently to overlapping regions produce a data race with undefined results. You must layer a synchronization primitive — a POSIX semaphore embedded in the shared region with `pshared=1`, or a `pthread_mutex_t` with `PTHREAD_PROCESS_SHARED` — on top. Additionally, the C compiler and CPU are free to reorder memory operations unless you use explicit barriers or `_Atomic` types.

The transfer cost of other mechanisms is worth quantifying. A pipe `write()`/`read()` pair copies data twice: userspace → kernel buffer, kernel buffer → userspace. Shared memory copies zero times:

$$\text{copy count} = \begin{cases} 0 & \text{shared memory} \\ 1 & \text{socket with } \texttt{MSG\_ZEROCOPY} \\ 2 & \text{pipe or standard socket} \end{cases}$$

### Sockets

A socket is a bidirectional communication endpoint. Unix domain sockets (`AF_UNIX`) connect processes on the same host through the kernel without touching any network stack; the kernel copies data directly between socket buffers. TCP sockets (`AF_INET`/`AF_INET6`, `SOCK_STREAM`) add reliable ordered delivery with retransmission, congestion control, and the accompanying latency. UDP sockets (`SOCK_DGRAM`) are unreliable and unordered but have lower per-message overhead because they skip connection state.

The key structural difference from pipes: sockets are bidirectional, can connect unrelated processes across machines, and support multiple simultaneous connections through `accept()`. The cost relative to shared memory is at minimum one copy per direction through the kernel socket buffer. Unix domain sockets also support `SCM_RIGHTS` ancillary messages — passing open file descriptors between processes — which no other mechanism supports.

### Signals

A signal is an asynchronous notification — just an integer — delivered by the kernel to a process or thread. Delivery interrupts the thread's current instruction stream and invokes either a registered handler or a default action (terminate, core dump, stop, or ignore). Signals carry essentially no data: POSIX `siginfo_t` adds sender PID and a small payload (`si_value`), but this is still tiny compared to any other IPC mechanism.

Signals are appropriate for **notification** ("a child exited," "a timer fired," "the terminal was resized"), not data transfer. Because a signal handler can fire between any two machine instructions, it can interrupt a function mid-execution — including inside `malloc()`, `printf()`, or any non-reentrant function. Only functions listed in the `signal-safety(7)` manual page (`write()`, `sem_post()`, `_exit()`, and a short list of others) are safe to call from a handler. Everything else risks deadlock or heap corruption.

## How It Works

### Pipe Internals

```c
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    int fd[2];
    if (pipe(fd) == -1) { perror("pipe"); return 1; }
    // fd[0] = read end, fd[1] = write end

    pid_t pid = fork();
    if (pid == 0) {
        /* child reads */
        close(fd[1]);               // close write end — child never writes
        char buf[64];
        ssize_t n = read(fd[0], buf, sizeof(buf) - 1);
        buf[n] = '\0';
        printf("child: %s\n", buf);
        close(fd[0]);
        _exit(0);
    } else {
        /* parent writes */
        close(fd[0]);               // close read end — parent never reads
        const char *msg = "hello via pipe";
        write(fd[1], msg, strlen(msg));
        close(fd[1]);               // EOF delivered once this closes
        wait(NULL);
    }
    return 0;
}
```

The `close(fd[0])` in the parent and `close(fd[1])` in the child are not optional cleanup — they are **load-bearing**. After `fork()`, both ends exist in both processes. The reference count on the write end is 2. The child's `read()` will block until the kernel sees zero open write-end references. If the parent closes `fd[1]` but the child forgets to close its copy of `fd[1]`, the child will block forever reading from itself.

**Atomicity guarantee:** A `write()` of at most `PIPE_BUF` bytes (defined as 4096 on Linux, inspectable via `fpathconf(fd[1], _PC_PIPE_BUF)`) is atomic with respect to other writers on the same pipe. Writes larger than `PIPE_BUF` may be interleaved. For a pipe with a single writer this is irrelevant, but for a logging pipe with multiple writers keeping messages under 4096 bytes prevents interleaving without any additional locking.

Pipe buffer capacity and the current byte count are visible through `fcntl`:

```c
int capacity = fcntl(fd[1], F_GETPIPE_SZ);   // default 65536
// increase if needed (requires CAP_SYS_RESOURCE for > /proc/sys/fs/pipe-max-size):
fcntl(fd[1], F_SETPIPE_SZ, 1 << 20);         // request 1 MiB
```

Sustained pipe throughput is bounded by how quickly the kernel can move data through the ring buffer relative to scheduling latency. A rough ceiling:

$$\text{throughput} \approx \frac{P_{\text{buf}}}{\text{RTT}_{\text{sched}}}$$

where $P_{\text{buf}}$ is the pipe buffer size and $\text{RTT}_{\text{sched}}$ is the round-trip scheduling latency (typically $50\text{–}200\,\mu\text{s}$ on an unloaded system). For a 64 KB buffer and $100\,\mu\text{s}$ latency, this gives roughly $640\,\text{MB/s}$ — consistent with empirical benchmarks.

#include <fcntl.h>

#include <unistd.h>

    struct mq_attr attr = {
        .mq_flags   = 0,
