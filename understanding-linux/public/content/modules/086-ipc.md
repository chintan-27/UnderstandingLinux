## Core Concepts
### Why IPC Exists
Processes in Linux operate in separate virtual address spaces enforced by the MMU. Without a mechanism to expose memory or exchange data, cooperation would be impossible. IPC solves three fundamental problems:  

1. **Data Transfer** – moving bytes from one address space to another.  
2. **Synchronization** – coordinating progress (e.g., producer/consumer).  
3. **Notification** – signaling asynchronous events (e.g., termination, I/O readiness).  

The choice of mechanism depends on *directionality*, *lifetime*, *granularity*, and *kernel involvement*.

### Classification of IPC Mechanisms
| Mechanism | Direction | Lifetime | Synchronization | Typical Use |
|-----------|-----------|----------|-----------------|-------------|
| **Unnamed pipe** | Half‑duplex (unidirectional) | Volatile (tied to creating process) | Kernel‑managed wake‑up queues | Parent‑child or related processes |
| **Named pipe (FIFO)** | Half‑duplex | Persistent (filesystem name) | Same as unnamed pipe | Unrelated processes on same host |
| **System V message queue** | Full‑duplex (via msg_type) | Kernel‑persistent until explicit `ipcrm` | Sender/receiver block on empty/full | Discrete‑message workloads, priority queues |
| **POSIX message queue (mqueue)** | Full‑duplex | Kernel‑persistent (mounted under `/dev/mqueue`) | Non‑blocking, timeout‑able, async notification | Real‑time apps, POSIX‑realtime extensions |
| **System V shared memory** | Bidirectional | Kernel‑persistent until `ipcrm` | Requires external sync (semaphores, mutexes) | Large‑volume data exchange, zero‑copy |
| **POSIX shared memory (shm_open)** | Bidirectional | Backed by `tmpfs` (visible under `/dev/shm`) | Same as System V | Portable, easier lifecycle |
| **UNIX domain socket** | Full‑duplex | Volatile (tied to socket lifespan) | Same as network sockets (select/poll/epoll) | Local client‑server, daemon communication |
| **Network socket (AF_INET/AF_INET6)** | Full‑duplex | Volatile | Same as UNIX domain | Cross‑host communication |
| **Signal** | Asynchronous notification | Instantaneous | Delivered via kernel interrupt; handler runs in target context | Error reporting, control events (SIGUSR1, SIGCHLD) |

### Underlying Principles
- **Zero‑copy vs. copy‑on‑write**: Shared memory avoids copying; pipes and message queues copy data into kernel buffers.  
- **Blocking semantics**: Most IPC syscalls block when the resource is unavailable unless `O_NONBLOCK` or timeout flags are set.  
- **Namespace**: Unnamed pipes are anonymous; named resources appear in a filesystem (FIFO, mqueue, shm) or kernel tables (System V IDs).

## How It Works
### Pipe Implementation (Unnamed & Named)
A pipe is a kernel‑maintained circular buffer with two wait queues: one for readers, one for writers.  
- **Capacity**: `PIPE_BUF` bytes (typically 4096). Writes ≤ `PIPE_BUF` are atomic when the pipe is empty or not full.  
- **Latency model**: For a payload of size *S*, the transfer time is  

$$
T_{\text{pipe}} = \frac{S}{B_{\text{mem}}} + T_{\text{wakeup}}
$$

where $B_{\text{mem}}$ ≈ memory bandwidth (≈20 GB/s on modern DDR4) and $T_{\text{wakeup}}$ is the scheduler latency (≈5‑15 µs).  

**Kernel data structures** (simplified):  

```c
struct pipe_inode_info {
    struct mutex   lock;
    struct wait_queue_head rd_wait;
    struct wait_queue_head wr_wait;
    unsigned int   head;      /* read index */
    unsigned int   tail;      /* write index */
    unsigned int   max_size;  /* PIPE_BUF */
    char           *buf;      /* kernel-allocated page */
    unsigned int   readers;
    unsigned int   writers;
    unsigned int   waiting_readers;
    unsigned int   waiting_writers;
    unsigned int   page_cache; /* number of allocated pages */
};
```

When `write()` is called, the kernel copies data from user space into `buf[tail]` (modulo `max_size`), increments `tail`, and wakes any waiter on `rd_wait`. `read()` mirrors the operation.

**Named pipe (FIFO)** lives in `pipefs` (a pseudo‑filesystem mounted internally). Creating a FIFO with `mkfifo()` simply inserts an inode into a regular filesystem that points to the same pipe internals.

### Message Queue Implementation
Both System V and POSIX queues store messages in kernel‑allocated structures; the difference lies in the API and namespace.

**System V `msg` layout** (from `<sys/msg.h>`):  

```c
struct msg {
    long            mtype;       /* message type */
    char            mtext[1];    /* variable length */
};
```

The kernel maintains a doubly‑linked list per queue. Each `msgsnd()` allocates a `struct msg` of size `sizeof(long) + msg_len` and inserts it at the tail. `msgrcv()` removes the first message whose `mtype` matches the requested type (or uses `MSG_EXCEPT`/`MSG_NOERROR`).  

**Complexity**: Insertion and removal are $O(1)$; scanning for a non‑FIFO type is $O(n)$ in the worst case.

**POSIX mqueue** (`mqueue.h`) uses a similar structure but is backed by a `tmpfs` mount (`/dev/mqueue`). Attributes (`struct mq_attr`) define `mq_maxmsg` and `mq_msgsize`. The kernel enforces these limits at creation time.

### Shared Memory Implementation
System V shared memory (`shmget`, `shmat`, `shmdt`) creates a segment of contiguous kernel pages that are later attached to a process’s address space via `vm_mmap`.  

**POSIX shm** (`shm_open`, `ftruncate`, `mmap`) is simpler:  

1. `shm_open()` creates or opens an object in `tmpfs` (mounted at `/dev/shm`).  
2. `ftruncate()` sets the object's size.  
3. `mmap()` maps the object into the caller’s address space with `PROT_READ|PROT_WRITE` and `MAP_SHARED`.  

Because the mapping is `MAP_SHARED`, any write to the mapped region updates the underlying `tmpfs` page, which is instantly visible to all other attached processes (cache coherency handled by the CPU).  

**Address calculation**: If the segment starts at address `base` and we want the *i*‑th element of type `T` (size `sizeof(T)`), the address is  

$$
\text{addr}_i = \text{base} + i \times \sizeof(T)
$$

### Socket Implementation (UNIX Domain)
UNIX domain sockets (`AF_UNIX`) behave like network sockets but the data never leaves the host. The kernel routes packets via the same socket layer but skips network device drivers.  

- **Stream (`SOCK_STREAM`)**: Provides a reliable, sequenced byte stream (similar to TCP). Internally, it uses a pair of linked socket buffers (`sk_buff`) with flow control.  
- **Datagram (`SOCK_DGRAM`)**: Preserves message boundaries (similar to UDP).  

File descriptor creation:  

```c
int sockfd = socket(AF_UNIX, SOCK_STREAM, 0);
struct sockaddr_un addr = {
    .sun_family = AF_UNIX,
    .sun_path   = "/tmp/my_sock"
};
bind(sockfd, (struct sockaddr *)&addr, sizeof(addr));
listen(sockfd, BACKLOG);
int connfd = accept(sockfd, NULL, NULL);
```

Data transfer uses the same `read()`/`write()` syscalls as pipes, but the underlying buffer is per‑socket.

### Signal Delivery
A signal is a kernel flag (`sigpending`) plus a context switch to invoke the handler. When `kill(pid, SIGNAL)` is called:

1. The kernel sets the corresponding bit in `task->signal.sigpending`.  
2. If the target is not blocking the signal, the kernel interrupts the target’s execution (via `do_signal()` on return to user mode) and forces it to jump to the handler address stored in `task->sighand->action[sig-1].sa_handler`.  
3. The handler runs on the target’s stack; upon return, the kernel clears the pending bit (unless the signal was set to `SA_RESTART` or similar).  

**Async‑signal‑safety**: Only a limited set of functions (listed in `signal-safety(7)`) may be safely called from a handler because they are reentrant and do not rely on mutable global state.

## Worked Examples
### Example 1: Pipe – Producer/Consumer with `fork`
**Goal**: Transfer 1 MiB of random data from producer to consumer, measuring throughput.

**producer.c**  

```c
#define _XOPEN_SOURCE 700
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <errno.h>

int main(void) {
    int pipefd[2];
    if (pipe(pipefd) == -1) {
        perror("pipe");
        exit(EXIT_FAILURE);
    }

    pid_t pid = fork();
    if (pid == -1) { perror("fork"); exit(EXIT_FAILURE); }

    if (pid > 0) {                 /* producer */
        close(pipefd[0]);          /* close unused read end */
        const size_t MB = 1024 * 1024;
        unsigned char *buf = malloc(MB);
        if (!buf) { perror("malloc"); exit(EXIT_FAILURE); }
        /* fill with pseudo‑random data */
        for (size_t i = 0; i < MB; ++i) buf[i] = (unsigned char)rand();

        ssize_t written = 0;
        while (written < MB) {
            ssize_t n = write(pipefd[1], buf + written, MB - written);
            if (n == -1) {
                if (errno == EINTR) continue;
                perror("write"); exit(EXIT_FAILURE);
            }
            written += n;
        }
        free(buf);
        close(pipefd[1]);          /* EOF for consumer */
        exit(EXIT_SUCCESS);
    } else {                       /* consumer */
        close(pipefd[1]);          /* close unused write end */
        unsigned char *buf = malloc(1024 * 1024);
        if (!buf) { perror("malloc"); exit(EXIT_FAILURE); }
        size_t read_total = 0;
        while (1) {
            ssize_t n = read(pipefd[0], buf, 1024 * 1024);
            if (n == 0) break;                /* EOF */
            if (n == -1) {
                if (errno == EINTR) continue;
                perror("read"); exit(EXIT_FAILURE);
            }
            read_total += n;
            /* optional: verify data */
        }
        fprintf(stderr, "Consumer received %zu bytes\n", read_total);
        free(buf);
        close(pipefd[0]);
        exit(EXIT_SUCCESS);
    }
}
```

**Explanation**  
- The pipe capacity (`PIPE_BUF = 4096`) forces the producer to loop; each `write()` call copies at most that many bytes into the kernel buffer.  
- The consumer loops until `read()` returns 0, indicating the writer closed its end.  
- Error handling retries on `EINTR` (signal‑interrupted syscalls).  

**Run & measure**  

```bash
$ gcc -O2 -Wall producer.c -o producer
$ ./producer
Consumer received 1048576 bytes
```

To see throughput, prepend `/usr/bin/time -v` or use `pv`:

```bash
$ ./producer 2>&1 | pv -b > /dev/null
1.00MiB 0:00:00 [ 210MiB/s] [=>                     ]
```

### Example 2: POSIX Message Queue – Priority Job Dispatcher
**Goal**: Send jobs with integer priorities; the worker extracts the highest‑priority job first.

**worker.c**  

```c
#define _XOPEN_SOURCE 700
#include <stdio.h>
#include <stdlib.h>
#include <mqueue.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>

#define QUEUE_NAME "/job_queue"
#define MAX_MSG 10
#define MSG_SIZE 256

typedef struct {
    long prio;          /* used as msg_type */
    char data[MSG_SIZE - sizeof(long)];
} job_t;

int main(void) {
    struct mq_attr attr = {
        .mq_flags   = 0,
        .mq_maxmsg  = MAX_MSG,
        .mq_msgsize = MSG_SIZE,
        .mq_curmsgs = 0
    };
    mqd_t mq = mq_open(QUEUE_NAME, O_CREAT | O_RDONLY, 0644, &attr);
    if (mq == (mqd_t)-1) { perror("mq_open"); exit(EXIT_FAILURE); }

    while (1) {
        job_t job;
        unsigned int prio;
        ssize_t n = mq_receive(mq, (char *)&job, MSG_SIZE, &prio);
        if (n == -1) {
            if (errno == EINTR) continue;
            perror("mq_receive"); break;
        }
        /* prio equals the msg_type we sent */
        printf("Received job prio=%ld: %s\n", job.prio, job.data);
        if (strcmp(job.data, "SHUTDOWN") == 0) break;
    }
    mq_close(mq);
    mq_unlink(QUEUE_NAME);
    return 0;
}
```

**sender.c**  

```c
#define _XOPEN_SOURCE 700
#include <stdio.h>
#include <stdlib.h>
#include <mqueue.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>

#define QUEUE_NAME "/job_queue"
#define MSG_SIZE 256

typedef struct {
    long prio;
    char data[MSG_SIZE - sizeof(long)];
} job_t;

int main(void) {
    struct mq_attr attr = {
        .mq_maxmsg  = 10,
        .mq_msgsize = MSG_SIZE,
        .mq_flags   = 0
    };
    mqd_t mq = mq_open(QUEUE_NAME, O_WRONLY, 0644, &attr);
    if (mq == (mqd_t)-1) { perror("mq_open"); exit(EXIT_FAILURE); }

    job_t jobs[] = {
        {3, "low priority"},
        {1, "high priority"},
        {2, "medium priority"},
        {0, "SHUTDOWN"}
    };
    for (size_t i = 0; i < sizeof(jobs)/sizeof(jobs[0]); ++i) {
        if (mq_send(mq, (const char *)&jobs[i], MSG_SIZE, jobs[i].prio) == -1) {
            perror("mq_send"); exit(EXIT_FAILURE);
        }
        printf("Sent job prio=%ld\n", jobs[i].prio);
        usleep(200000); /* stagger sends */
    }
    mq_close(mq);
    return 0;
}
```

**Explanation**  
- The queue is created with `mq_open(O_CREAT|O_RDONLY)` in the worker and `O_WRONLY` in the sender; both refer to the same underlying object because the name (`/job_queue`) is looked up in the `mqueue` filesystem.  
- `mq_send()`’s fourth argument is the *priority*; the kernel orders the internal list by descending priority (numeric value). Lower numbers = higher priority in this example because we used the raw integer as priority.  
- The worker calls `mq_receive()` which blocks until a message arrives; the returned `prio` (the `msg_type`) is the priority used during `mq_send`.  

**Run**  

```bash
$ gcc -Wall -lrt worker.c -o worker
$ gcc -Wall -lrt sender.c -o sender
$ ./worker &
[1] 12345
$ ./sender
Sent job prio=3
Sent job prio=2
Sent job prio=1
Sent job prio=0
Received job prio=1: high priority
Received job prio=2: medium priority
Received job prio=3: low priority
Received job prio=0: SHUTDOWN
```

### Example 3: POSIX Shared Memory – Ring Buffer with Futex‑Based Synchronization
**Goal**: Demonstrate zero‑copy exchange of 64‑bit integers between two processes using a lock‑free ring buffer and futexes for efficient waiting.

**common.h**  

```c
#ifndef COMMON_H
#define COMMON_H
#include <stdint.h>
#define RING_SIZE 1024   /* must be power of two */
#define MASK (RING_SIZE-1)
typedef struct {
    uint64_t buffer[RING_SIZE];
    /* futex words: 0 = empty, 1 = data present */
    volatile int32_t head;   /* index written by producer */
    volatile int32_t tail;   /* index consumed by consumer */
} ring_t;
#endif
```

**producer.c**  

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>
#include <errno.h>
#include <sys/syscall.h>
#include <linux/futex.h>
#include "common.h"

static inline int futex_wait(volatile int32_t *addr, int32_t val) {
    return syscall(SYS_futex, addr, FUTEX_WAIT, val, NULL, NULL, 0);
}
static inline int futex_wake(volatile int32_t *addr) {
    return syscall(SYS_futex, addr, FUTEX_WAKE, 1, NULL, NULL, 0);
}

int main(void) {
    int fd = shm_open("/ring_shm", O_CREAT | O_RDWR, 0644);
    if (fd == -1) { perror("shm_open"); exit(EXIT_FAILURE); }
    if (ftruncate(fd, sizeof(ring_t)) == -1) { perror("ftruncate"); exit(EXIT_FAILURE); }
    ring_t *ring = mmap(NULL, sizeof(ring_t), PROT_READ|PROT_WRITE,
                        MAP_SHARED, fd, 0);
    if (ring == MAP_FAILED) { perror("mmap"); exit(EXIT_FAILURE); }
    close(fd);

    /* initialize */
    ring->head = ring->tail = 0;

    const size_t N = 1<<20;   /* 1M items */
    for (size_t i = 0; i < N; ++i) {
        uint64_t val = i * i; /* some workload */
        int32_t my_head = ring->head;
        int32_t next = (my_head + 1) & MASK;
        /* wait if full */
        while (next == ring->tail) {
            futex_wait(&ring->tail, ring->tail);
        }
        ring->buffer[my_head] = val;
        ring->head = next;    /* publish */
        futex_wake(&ring->head); /* wake consumer */
    }
    /* send poison pill */
    while (((ring->head + 1) & MASK) == ring->tail) futex_wait(&ring->tail, ring->tail);
    ring->buffer[ring->head] = UINT64_MAX;
    ring->head = (ring->head + 1) & MASK;
    futex_wake(&ring->head);
    munmap(ring, sizeof(ring_t));
    shm_unlink("/ring_shm");
    return 0;
}
```
