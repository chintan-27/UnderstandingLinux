## Core Concepts
### Why Virtual Memory Exists
Virtual memory solves three tightly coupled problems that bare‑metal addressing cannot:

1. **Isolation & Protection** – each process must see its own address space; a bug in one process must not corrupt another’s memory or kernel data.
2. **Efficient Use of Limited RAM** – physical memory is far smaller than the cumulative virtual address spaces of all running programs. By keeping only actively used pages in RAM and paging the rest to disk, the system can run more (and larger) programs than RAM would allow.
3. **Simplified Programming Model** – programmers allocate and free memory via `malloc`/`free` (or `mmap`/`munmap`) without worrying about where the underlying physical frames live.

These goals are achieved by the **Memory Management Unit (MMU)**, a hardware component that translates every virtual address (VA) generated by the CPU into a physical address (PA) before the memory access reaches RAM.

### Page Size, Offset, and Virtual‑Page Number
The MMU works on fixed‑size blocks called *pages*. Let the page size be \(P = 2^{\text{page\_shift}}\) bytes.  
For a virtual address \(VA\):

\[
\text{offset} = VA \bmod P = VA \,\&\, (2^{\text{page\_shift}}-1)
\]
\[
\text{virtual page number (VPN)} = \left\lfloor \frac{VA}{P} \right\rfloor = VA \gg \text{page\_shift}
\]

The offset is unchanged by translation; only the VPN is replaced by a *physical page number* (PFN). Hence:

\[
PA = (PFN \ll \text{page\_shift}) \;|\; \text{offset}
\]

Typical Linux systems use \(P = 4096\) bytes → \(\text{page\_shift}=12\). On a 32‑bit VA, VPN occupies the high 20 bits; on a 64‑bit VA, the high 52 bits (assuming a 4‑level page table).

### Page Table Structure
A *page table* maps each VPN to a PFN together with protection and status bits:

| Bit(s) | Meaning |
|--------|---------|
| PFN    | Physical frame number (page‑aligned base address) |
| accessed (A) | Set by hardware on any read/write; used by OS for page‑replacement algorithms |
| dirty (D)   | Set on a write; indicates the page must be written back to disk before reclamation |
| read/write (R/W) | Permission bits; a fault occurs if the access type violates them |
| user/supervisor (U/S) | Controls whether kernel or user mode may access the page |
| present (P)   | If clear, triggers a page‑fault (page not resident) |
| global (G)    | Ignores ASID in TLB lookup (kernel pages) |
| …            | Architecture‑specific bits (e.g., NX, PAT) |

Because a linear page table for a 64‑bit address space would be impossibly large, modern OSes use *hierarchical* (multi‑level) page tables. Each level indexes a slice of the VPN; the walk stops at the level that holds the final PTE (Page Table Entry). For example, x86‑64 with 4 KB pages uses four levels: PGD → PUD → PMD → PTE, each indexed by 9 bits of the VPN (9×4=36) plus the 12‑bit offset = 48‑bit canonical VA.

### Translation Lookaside Buffer (TLB)
The TLB is a small, fully‑associative cache of recently used PTEs. Without it, every memory reference would require a page‑table walk (multiple RAM reads), adding tens of cycles to each access. The TLB exploits *temporal locality*: programs tend to reuse the same pages over short intervals.

On a TLB **hit**, the MMU returns the PFN in a single cycle (or a few cycles). On a **miss**, the MMU walks the page‑table hierarchy, fetches the PTE, updates the accessed/dirty bits, inserts the entry into the TLB (possibly evicting an old one), and then retries the translation.

### Page Faults
If the PTE’s *present* bit is clear, the MMU raises a page‑fault exception. The kernel’s page‑fault handler:

1. Checks whether the VA is valid (looks up the `vm_area_struct` covering the address).  
2. If valid but not resident, allocates a free physical frame, schedules I/O to read the page from swap or a file-backed storage, updates the PTE with the new PFN, sets present=1, and clears the fault.  
3. If the access violates permissions, sends `SIGSEGV` to the faulting process.  
4. If the VA is outside any VMA, also sends `SIGSEGV`.

After handling, the instruction that caused the fault is restarted; the TLB is then populated with the new mapping.

## How It Works
### End‑to‑End Address Translation (TLB‑hit path)
1. CPU issues VA.  
2. MMU splits VA into `<VPN, offset>` using the page‑shift constant.  
3. MMU looks up VPN in the TLB (associative match).  
4. On hit, TLB yields `<PFN, perm‑bits>`.  
5. MMU checks perm‑bits against the current CPU mode and access type (read/write/execute).  
6. If permitted, computes PA = `(PFN << page_shift) | offset`.  
7. PA drives the address bus to RAM/cache.

### TLB‑miss path (page‑table walk)
1. Steps 1‑2 as above.  
2. TLB miss → initiate hardware page‑table walk:  
   - Read PGD entry using `CR3` (base of top‑level table) + PGD‑index·sizeof(pte).  
   - If PGD entry present, read PUD entry using PGD‑PFN + PUD‑index·sizeof(pte).  
   - Continue through PMD → PTE levels.  
3. At the final level, fetch the PTE.  
4. Update accessed (A) bit; if write and D clear, set D.  
5. Insert `<VPN, PFN, perm‑bits>` into TLB (replacement policy: LRU or random).  
6. Retry translation; now it hits.

### Page‑fault handling (software path)
1. TLB miss → page‑table walk → finds PTE with `P=0`.  
2. MMU raises page‑fault exception → vectors to `do_page_fault()` in the kernel.  
3. Kernel finds the `vm_area_struct` covering the faulting VA (via the process’s `mm->mmap` RBTree).  
4. Checks protection flags; if illegal → `SIGSEGV`.  
5. If the area is anonymous (heap/stack) or file‑backed, allocates a free page (`alloc_page()`), zero‑fills or reads from backing store, updates the PTE, sets `P=1`, `A=0`, `D=0` as appropriate.  
6. Invalidates any stale TLB entry (`invlpg` or `flush_tlb_single`).  
7. Returns to user mode; the faulting instruction restarts and now hits in the TLB.

## Worked Examples
### Example 1: TLB Hit – 4 KB pages, 32‑bit VA
*Parameters*: page size = 4096 B → `page_shift = 12`.  
Virtual address: `VA = 0x100030A0`.

**Step‑by‑step**

1. Split VA:  
   - `offset = VA & 0xFFF = 0x0A0`.  
   - `VPN = VA >> 12 = 0x10003`.  
2. TLB lookup finds entry: `<VPN=0x10003, PFN=0x7AF2, perm=RW>`.  
3. Permission check: user mode read → allowed.  
4. Compute PA:  
   - `PFN << 12 = 0x7AF2000`.  
   - `PA = 0x7AF2000 | 0x0A0 = 0x7AF20A0`.  
5. CPU issues read to physical address `0x7AF20A0`.

### Example 2: TLB Miss → Page‑Table Walk → Page Fault (Anonymous Memory)
*Parameters*: same page size.  
Process has a single `vm_area_struct` covering `0x08048000–0x0806A000` (heap) with `VM_READ|VM_WRITE`.  
Page table currently has no entry for VPN `0x08049`.

**Virtual address**: `VA = 0x08049120`.

1. Split: `offset = 0x120`, `VPN = 0x08049`.  
2. TLB miss → start walk:  
   - PGD index = bits 31‑22 of VPN = `0x2`.  
   - PGD[2] points to a valid PUD table (PFN = `0x3C00`).  
   - PUD index = bits 21‑13 = `0x1`.  
   - PUD[1] points to a valid PMD table (PFN = `0x3C10`).  
   - PMD index = bits 12‑4 = `0x0`.  
   - PMD[0] points to a valid PTE table (PFN = `0x3C20`).  
   - PTE index = bits 3‑0 = `0x9`.  
   - PTE[9] reads `0x0` (present=0).  
3. Since `P=0`, MMU raises page‑fault.  
4. Kernel handler: finds VMA covering `0x08049000`; area is anonymous → allocates a free page, say PFN = `0x4D50`.  
5. Writes PTE: `| PFN=0x4D50 | present=1 | RW=1 | user=1 | accessed=0 | dirty=0`.  
6. Inserts `<VPN=0x08049, PFN=0x4D50>` into TLB.  
7. Retries translation: now TLB hit → PA = `(0x4D50 << 12) | 0x120 = 0x4D50120`.  
8. The original load/store completes to physical address `0x4D50120`.

### Example 3: TLB Hit with Dirty Bit Update (Write)
Same VA as Example 1, but the access is a **store**.

1. TLB hit returns PFN=`0x7AF2`, perm bits include `RW=1`, `D=0`.  
2. Write permission check passes.  
3. PA computed as before (`0x7AF20A0`).  
4. The store updates memory at that PA.  
5. MMU hardware (or the page‑table walk on next miss) sets the dirty bit in the PTE to `1`.  
6. On subsequent context switch, the kernel will know this page must be written back to swap before reclamation.

## Common Mistakes
| # | Mistake | Why It’s Wrong |
|---|---------|----------------|
| 1 | **Assuming the TLB stores full virtual addresses** | The TLB only stores the *VPN* (or a tag derived from it) and the corresponding PFN plus permission bits. Storing the full VA would waste space and defeat the purpose of a cache; the offset is never needed for translation. |
| 2 | **Believing a larger page size always improves performance** | Larger pages reduce TLB miss rate but increase internal fragmentation and can worsen page‑fault latency (more data must be swapped in/out). The optimal size balances TLB coverage against memory waste; Linux supports huge pages (2 MiB/1 GiB) precisely for workloads where the trade‑off favors them. |
| 3 | **Thinking the page table entry contains the virtual address** | A PTE holds the *physical* frame number and control bits. The virtual address is implicit from the index used to locate the PTE; storing it would be redundant and would break hierarchical walks. |
| 4 | **Confusing “present” bit with “loaded in RAM”** | `present=0` can also mean the page is swapped out *or* that the address is unmapped (a hole). The kernel distinguishes these cases by consulting the VMA list; a missing VMA yields a segmentation fault, not a page‑in from swap. |
| 5 | **Assuming every page fault results in disk I/O** | Faults on demand‑zero pages (e.g., newly allocated stack) are satisfied by zero‑filling a fresh frame—no disk access. Faults on file‑mapped pages may read from the page cache, which may already be in RAM, avoiding disk. |

## Exercises
### 1. Easy – Address Decomposition
Given a system with 4 KB pages and a 32‑bit virtual address space, compute the VPN and offset for `VA = 0xAFC3E7`. Show your work in binary and hex.

### 2. Medium – TLB Miss Penalty
Assume:
- L1 data cache hit latency = 4 cycles.  
- L2 cache hit latency = 12 cycles.  
- Main memory access latency = 100 cycles.  
- A page‑table walk requires reading 4 PTEs (one per level) from memory, each uncached.  
- TLB hit latency = 1 cycle (the tag compare).  

Calculate the average memory‑access time (AMAT) for a load when the TLB hit rate is 95 %. Show the formula and numeric result.

### 3. Hard – Two‑Level Page Table Sizing
A hypothetical architecture uses 8 KB pages (`page_shift = 13`) and 32‑bit virtual addresses. Design a two‑level page table where the outer level (page directory) indexes the high bits of the VPN and the inner level (page table) indexes the low bits.  
- Determine the number of bits allocated to each level.  
- Compute the size (in bytes) of a single page directory entry (PDE) and a single page‑table entry (PTE) assuming each entry is 8 bytes.  
- Calculate the worst-case memory consumption of the page table for a process that uses the entire virtual address space (i.e., all pages allocated).  

Provide the derivations and final numeric answer.

### 4. Very Hard – Measuring TLB Activity on Linux
Write a short C program that allocates a large array (>> TLB size) and accesses it with a stride that guarantees a TLB miss on every iteration. Use `perf stat` to measure the number of `dTLB-load-misses` and `dTLB-loads`. Show the commands you would run, the expected output format, and explain how the results confirm your stride choice.

## Linux Connection
### Kernel Data Structures
- `struct mm_struct` – represents a process’s address space; pointed to by `task_struct->mm`.  
- `struct vm_area_struct` (VMA) – describes a contiguous virtual memory region with flags (`VM_READ`, `VM_WRITE`, `VM_EXEC`, `VM_SHARED`, etc.). Stored in a red‑black tree (`mm->mmap`) and also as a doubly‑linked list (`mm->mmap_list`).  
- Page‑table types (x86‑64): `pgd_t`, `pud_t`, `pmd_t`, `pte_t`. Each is an unsigned long holding the PFN and bits.  
- The macro `PAGE_SHIFT` (usually 12) and `PAGE_SIZE` (`1 << PAGE_SHIFT`) are defined in `<asm/page.h>`.

### Key Interfaces
| Syscall / File | Purpose |
|----------------|---------|
| `void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);` | Creates a VMA; `prot` maps to PTE permission bits; `flags` control sharing (`MAP_PRIVATE`, `MAP_SHARED`) and anonymity (`MAP_ANONYMOUS`). |
| `int munmap(void *addr, size_t length);` | Removes the VMA(s) covering the range; updates VMAs and tears down page‑table entries. |
| `int mprotect(void *addr, size_t length, int prot);` | Changes protection bits of existing PTEs; triggers a TLB flush (`flush_tlb_range`). |
| `int mincore(void *addr, size_t length, unsigned char *vec);` | Returns which pages are resident (checks the `present` bit). |
| `int madvise(void *addr, size_t length, int advice);` | Advice like `MADV_WILLNEED`, `MADV_DONTNEED`, `MADV_HUGEPAGE` influences page‑reordering and transparent huge pages (THP). |
| `int mlock(void *addr, size_t length);` / `munlock` | Pins pages in RAM (clears the `swap` bits). |

### Inspecting Virtual Memory from Userspace
```bash
# Show a process’s memory map (VMAs)
$ cat /proc/$$/maps
00400000-0040b000 r-xp 00000000 08:02 1234567 /bin/bash
0060a000-0060b000 r--p 0000a000 08:02 1234567 /bin/bash
0060b000-0060e000 rw-p 0000b000 08:02 1234567 /bin/bash
7ffd8c3e2000-7ffd8c403000 rw-p 00000000 00:00 0   [stack]
...

# Display summary stats (page faults, swapping, etc.)
$ vmstat -s
      123456 pages swapped in
      234567 pages swapped out
      345678 pages faulted
      456789 major page faults
      ...

# Show per‑process fault counters
$ cat /proc/$$/stat | awk '{print $10,$11}'   # minflt, majflt
1234 56

# Examine the raw page‑table entries (requires root)
$ sudo cat /proc/$$/pagemap | \
    dd bs=8 count=1 skip=$((0x10000000>>9)) 2>/dev/null | \
    od -An -t x8
```
*Explanation*: `/proc/pagemap` contains an array of 8‑byte entries, one per virtual page. The index is `VPN >> (PAGE_SHIFT-3)` because each entry is 8 bytes. The example extracts the entry for VA `0x10000000`.

### Managing Swappiness and Huge Pages
```bash
# View current swappiness ( tendency to swap out anonymous pages )
$ cat /proc/sys/vm/swappiness
60

# Set to 10 (less swapping) – requires root
$ sudo sysctl -w vm.swappiness=10

# Enable transparent huge pages for a specific madvise region
$ echo always > /sys/kernel/mm/transparent_hugepage/enabled
$ madvise(ptr, length, MADV_HUGEPAGE);
```

### Example: Using `mmap` to Map a File
```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int fd = open("/etc/passwd", O_RDONLY);
    if (fd < 0) { perror("open"); exit(1); }

    off_t len = lseek(fd, 0, SEEK_END);
    void *addr = mmap(NULL, len, PROT_READ, MAP_PRIVATE, fd, 0);
    if (addr == MAP_FAILED) { perror("mmap"); exit(1); }

    /* First byte of the file */
    putchar(((char *)addr)[0]);

    munmap(addr, len);
    close(fd);
    return 0;
}
```
Compile with `gcc -Wall -O2 mmap_example.c -o mmap_example`. The resulting VMA appears in `/proc/self/maps` as a range with `r--p` flags and the file offset shown.

## Why This Matters
Virtual memory is the invisible foundation that lets modern Linux systems:

* **Run large, complex applications** – browsers, databases, and containers can allocate gigabytes of virtual memory while only a fraction resides in RAM, thanks to demand paging and swapping.
* **Provide strong isolation** – each process gets its own `mm_struct` and set of VMAs; bugs cannot corrupt another process’s memory, and the hardware enforces read/write/execute permissions via the PTE bits.
* **Enable security features** – Address Space Layout Randomization (ASLR) works by randomly shifting the base of `vm_area_struct`s; the MMU still translates those randomized addresses correctly.
* **Support efficient I/O** – `mmap` lets the kernel treat file data as memory, eliminating extra copy operations; the page cache backs the mapped pages, and dirty bits guide write‑back.
* **Allow fine‑grained tuning** – administrators adjust swappiness, transparent huge pages, and `vm.max_map_count` to match workload characteristics, directly influencing the frequency of TLB misses, page‑fault rates, and overall latency.

Understanding the mechanics—how the MMU splits addresses, how hierarchical page tables conserve memory, how the TLB exploits locality, and how the kernel handles faults—equips you to diagnose performance spikes, size swap space correctly, choose appropriate page sizes, and write systems code that interacts safely and efficiently with the Linux memory subsystem. Mastery of these concepts transforms you from a user of Linux into someone who can shape its behavior.
