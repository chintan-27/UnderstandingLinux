## Why This Matters

A network that appears to work is not the same as a network that works correctly. Packets get dropped silently. TCP windows shrink without warning. MTU mismatches cause retransmits nobody notices. Latency spikes appear only under load. Without observability tools, you are debugging blind — guessing at causes for symptoms that could be a misconfigured NIC, a kernel buffer too small, a routing loop, or a firewall dropping RSTs.

The tools here address different layers: `tcpdump` sees bytes on the wire; `ss` sees kernel socket state; `ethtool` sees NIC hardware configuration; `perf` sees where CPU time goes in the kernel; eBPF sees arbitrary kernel execution paths in real time. Understanding what each tool actually does — which kernel interface it uses, what data it reads, why that data is authoritative — is the difference between using these tools and understanding them.

## Core Concepts

### Packet Capture: tcpdump

`tcpdump` places the NIC into promiscuous mode and attaches a **BPF (Berkeley Packet Filter)** program to a `PF_PACKET` socket in the kernel. The filter runs in kernel space before any data is copied to userspace. Packets that don't match are discarded at the `sk_buff` level, never crossing the user/kernel boundary via `copy_to_user`. This is why high-rate capture is feasible: the cost of a non-matching packet is the cost of running a short BPF program, not a context switch plus memory copy.

The BPF bytecode is a register-based instruction set. When you write `tcpdump -i eth0 'tcp port 22'`, `libpcap` compiles that expression into BPF instructions and loads them via `setsockopt(fd, SOL_SOCKET, SO_ATTACH_FILTER, ...)`. You can inspect the generated bytecode with `-d`:

```bash
tcpdump -i eth0 'tcp port 22' -d
```

### Socket State: ss

`ss` reads per-socket state from the kernel via **netlink** (specifically `NETLINK_INET_DIAG` messages), not by parsing `/proc/net/tcp`. The netlink path is faster because the kernel serializes only what you request; `/proc/net/tcp` requires the kernel to format the entire TCP socket table as ASCII text regardless of what you actually need. The data includes fields maintained inside `struct tcp_sock`: send/receive buffer occupancy, congestion window (`snd_cwnd`), slow-start threshold (`snd_ssthresh`), retransmit counter, and RTT estimates.

### Interface Configuration and Routing: iproute2

`iproute2` (`ip`, `tc`, `bridge`) communicates with the kernel via **rtnetlink** sockets (`NETLINK_ROUTE`). It replaced `ifconfig` and `route` because those tools used `ioctl`-based interfaces (`SIOCGIFADDR`, `SIOCADDRT`, etc.) that could not express the kernel's actual routing model: policy routing with multiple tables (`/etc/iproute2/rt_tables`), network namespaces, ECMP routes, or traffic control queuing disciplines. `ifconfig` and `route` are a lossy projection of a richer kernel structure.

### Hardware Diagnostics: ethtool

`ethtool` uses the kernel's `ethtool` interface, which dispatches to driver-specific function pointers in `struct ethtool_ops` (defined in `include/linux/ethtool.h`). The driver's implementation reads from or writes to NIC registers. This is the only userspace path to the actual hardware configuration — link speed, duplex, auto-negotiation state, offload capabilities (checksum offload, TSO, LRO, GRO), interrupt coalescing timers, and ring buffer sizes. None of this is visible via `ip` or `ss`.

### Performance Counting: perf

`perf` is the userspace interface to the kernel's `perf_events` subsystem. It can count hardware PMU events (cache misses, branch mispredictions, CPU cycles via `PERF_TYPE_HARDWARE`), software events (`PERF_TYPE_SOFTWARE`: context switches, page faults), and kernel tracepoints (`PERF_TYPE_TRACEPOINT`). For networking, it tells you *where* CPU time is spent — in `ksoftirqd`, in `tcp_rcv_established`, in a driver's NAPI poll loop — which a packet capture cannot tell you.

### Tracing: tracepoints, kprobes, eBPF

Linux exposes **static tracepoints** placed by kernel developers at semantically meaningful locations (e.g., `net:net_dev_queue`, `tcp:tcp_retransmit_skb`), listed in `/sys/kernel/debug/tracing/events/`. **kprobes** let you attach dynamically to any kernel instruction address. **eBPF** programs are JIT-compiled bytecode loaded into the kernel and attached to probe points; the kernel verifier checks them for safety (no unbounded loops, no out-of-bounds memory access) before they run. The result is arbitrary kernel instrumentation with overhead measured in nanoseconds per event.

## How It Works

### BPF Filtering in tcpdump

```
Packet arrives at NIC driver
       ↓
   sk_buff allocated in kernel
       ↓
   BPF filter evaluated          ← runs in kernel context, no syscall
       /              \
  match                no match → skb freed, nothing copied
       ↓
  copy_to_user → userspace ring buffer
       ↓
  tcpdump reads, calls libpcap dissector
```

The filter `'tcp port 22 and not host 10.0.0.1'` discards non-matching packets before `copy_to_user` is ever called. Capturing everything and filtering in userspace (`tcpdump -i eth0 | grep ...`) performs the `copy_to_user` for every packet, which saturates the bus and increases latency under load.

Dump the compiled BPF bytecode to verify what the kernel actually runs:

```bash
tcpdump -i eth0 'tcp port 22 and not host 10.0.0.1' -d
# (0) ldh [12]       load ethertype
# (1) jeq #0x800     jump if IPv4
# ...
```

A tcpdump line for a TCP data segment:

```
20:20:29.674713 IP (tos 0x8, ttl 64, id 57680, flags [DF], proto TCP, length 1452)
  10.0.0.123.1027 > 169.229.62.97.22: . 2831:4231(1400) ack 2105 win 65535
```

Each field is a decoded header value:

| Field | Meaning |
|---|---|
| `flags [DF]` | Don't Fragment bit set; PMTUD is active |
| `2831:4231(1400)` | Sequence range; 1400 bytes of payload |
| `ack 2105` | Cumulative acknowledgment number |
| `win 65535` | Receive window advertised to the remote end |

The TCP receive window imposes a hard throughput ceiling:

$$\text{Throughput} \leq \frac{W}{RTT}$$

where $W$ is the window size in bytes. For a 64 KB window over a 100 ms RTT:

$$\frac{65{,}535 \text{ bytes}}{0.100 \text{ s}} = 655{,}350 \text{ bytes/s} \approx 640 \text{ KB/s}$$

A 1 Gb/s link delivers:

$$\frac{10^9 \text{ bits/s}}{8 \text{ bits/byte}} = 125 \text{ MB/s}$$

The window constrains throughput to $\approx 0.5\%$ of link capacity. This is not a congestion problem — it is a window size problem. TCP window scaling (RFC 1323) extends the window field from 16 bits to an effective 30 bits by multiplying the raw 16-bit value by $2^k$ where $k$ is the scaling factor negotiated in the SYN/SYN-ACK. Without it, the maximum window is $65{,}535$ bytes and the bandwidth-delay product cannot be filled on any high-latency path.

The bandwidth-delay product is:

$$\text{BDP} = \text{Bandwidth} \times \text{RTT}$$

For a 1 Gb/s link with 100 ms RTT:

$$\text{BDP} = 125 \times 10^6 \text{ bytes/s} \times 0.100 \text{ s} = 12{,}500{,}000 \text{ bytes} \approx 11.9 \text{ MB}$$

The send buffer must be at least this large to keep the pipe full. The kernel's default (`net.ipv4.tcp_wmem`) is typically 4 MB, which is already a bottleneck on high-BDP paths.

### PMTUD Failure Visible in tcpdump
